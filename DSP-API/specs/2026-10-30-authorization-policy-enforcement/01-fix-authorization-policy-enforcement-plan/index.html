    fix: close the triaged authorization gaps and make every endpoint declare its authorization policy

    Overview

    Three security issues in triage (DEV-7712, DEV-7713, DEV-7714) are real. Two more fail-open gaps of the same kind turned up during research. Three filed follow-ups were verified and pulled in: DEV-7723 (fail-open), DEV-7721 and DEV-7722 (latent: wrong admin checks that the permission comparison masks today, see Phase 7). This plan fixes all eight and adds the structure that makes this bug class visible:

    • every endpoint declares an authorization policy;
    • a ratchet test fails on any new endpoint without one;
    • a lint step fails on the two code shapes behind the bugs;
    • a pilot migrates the admin lists and v2 standoff slices to the new model;
    • an authorization matrix test checks the pilot endpoints per principal.

    One plan, one PR, as the owner decided. The eight fixes come first as self-contained fix: commits.

    Problem Statement / Motivation

    The bugs. Every one is a hand-written check that is missing, swallowed, or given the wrong identity:

    Id Where Defect Effect
    DEV-7713 AdminListRestService.scala:116, ListsResponder.scala:1048-1059 @unused user; no role check Any logged-in user deletes list-node comments in any project, irreversibly
    DEV-7714 StandoffRestService.scala:36, StandoffResponderV2.scala:54-69 Only ensureUserIsNotAnonymous Any logged-in user writes a mapping into any project's data graph (no overwrite: StandoffResponderV2.scala:277-282)
    DEV-7712 ResourcesResponderV2.scala:1160-1165, :1467-1481 Preview read as SystemUser; .resources.head on a filtered result Anonymous callers get dates and author IRIs of hidden resources; project history fails (403, measured; 500 was assumed) when one resource is hidden
    new CreateResourceV2Handler.scala:102-105 ensureNotAnonymousUser ends in .ignore The anonymous check never fires; only the later create-permission check stands
    new modules/ingest/.../ReportEndpointsHandler.scala:21 serverLogic(_ => _ => ...) drops the principal Any valid JWT starts a forked all-project report, although the endpoint is documented as admin-only
    DEV-7723 ValuesResponderV2.scala:1144 (canRemoveValue) Resource read as SystemUser; class, value and type errors before the permission check Any logged-in user probes a hidden resource's class and its values' IRIs and types
    DEV-7721 ValuesResponderV2.scala:268 isProjectAdmin(requestingUser.id) passes the user IRI The admin exemption never applies; masked today (Phase 7)
    DEV-7722 CreateResourceV2Handler.scala:359-361 !(isProjectAdmin && !isSystemAdmin) SystemAdmins are not exempt; masked today (Phase 7)

    The structure behind them. These are verified in code, not just suspected:

    • BaseEndpoints (slice/common/api/BaseEndpoints.scala) only authenticates. securedEndpoint, withUserEndpoint and publicEndpoint hand a User to the server logic. Whether that user is authorized is up to each handler. The one exception is bearerSystemAdminEndpoint, which authorizes in the security logic and is used by one route.
    • Authorization is a hand-called AuthorizationRestService.ensure* in about 86 RestService methods. About 37 more are checked in responders through other mechanisms: ListsResponder.ensureUserIsAdminOrProjectOwner, OntologyCacheHelpers.checkPermissionsForOntologyUpdate, RestCardinalityService, ResourceUtilV2.check*Permission, and inline checks. That is about 13 overlapping mechanisms. The ontology one re-implements the project-admin rule without the active-user check.
    • Nothing ties an endpoint to a required role. The .description("Requires ...") strings are prose, and for DEV-7713 and DEV-7714 they describe the bug ("Requires authentication.").
    • SystemUser passes every role check, in four independent places (AuthorizationRestService.isSystemAdminOrUser, PermissionUtilADM:95, ScopeResolver, UserRestService:217). So reading "as SystemUser" silently bypasses object permissions (DEV-7712). Non-test SystemUser references sit in 13 main-source files (word-bounded match on *.scala under modules/*/src/main, so isSystemUser does not count; some hits are comments).
    • -Wunused:all -Werror would flag an ignored user parameter, but @unused silences it (DEV-7713).
    • No test checks authorization across endpoints. test-e2e/.../EndpointsE2ESpec.scala enumerates every server endpoint but only asserts that it has an HTTP method. Negative authorization tests are per endpoint and uneven: the delete-comments test only uses rootUser.

    Proposed Solution

    Use the XACML / NIST ABAC vocabulary, mapped onto the monolith in-process:

    • PDP (decision point): AuthorizationRestService, the existing single home of the role rules. Nothing new re-implements them.
    • PEP (enforcement point):
      • Function-level policies that depend only on the user (SystemAdmin, Authenticated) are enforced by the endpoint base in the tapir security logic, before the body is decoded. This generalises bearerSystemAdminEndpoint.
      • Project-scoped policies need the decoded input to find the project, so they cannot be decided in the security logic. The endpoint factory for these policies therefore does not hand the handler a User. It hands over a ProjectCandidate, which exposes nothing a handler can act on. The only way to turn it into something usable is to ask the PDP: authorizeProjectAdmin(candidate, projectIri) returns a grant, and the domain write methods accept only that grant. A handler that skips the check has no user to pass on and no grant to call the domain with, so the omission does not compile.
      • Object-level permissions (view, modify, delete, change-rights on resources and values) stay where the owning domain loads the object, as the domain modularization reasoning (dasch-specs, 2026-07-30) decided.
    • Declaration: every endpoint carries a Policy value as a tapir attribute (precedent: NegotiatesOwnAccept.key). The attribute is the machine-readable statement of what the endpoint requires. Tests read it.
    • Default-deny by ratchet: a test fails when an endpoint has no Policy and is not in a checked-in baseline, and when the baseline lists an endpoint that has since gained one. The baseline can only shrink.
    • Lint: just check fails on @unused on a User parameter, and on SystemUser in a main-source file, each outside its allow-list.

    No external policy engine (Cedar, OPA, OpenFGA). Not one of them stops a forgotten call, which is the bug class here. The rule set is small: three roles plus four object permissions. And object permissions live in RDF, so an engine would need a sync layer that is itself an authorization risk.

    Policy model (sketch)

    // slice/common/api/Policy.scala
enum Policy {

  /** No credentials needed; the reason is reviewed because every public route is an exposure decision. */
  case Public(reason: String)

  /** Any active, non-anonymous user. Reviewed because "logged in" alone was the DEV-7713/DEV-7714 bug class. */
  case Authenticated(reason: String)

  case SystemAdmin

  /** SystemAdmin, or ProjectAdmin of the project named by `projectFrom` (e.g. "path projectIri", "list node"). */
  case ProjectAdmin(projectFrom: String)

  /** SystemAdmin, ProjectAdmin or member of the project named by `projectFrom`. */
  case ProjectMember(projectFrom: String)

  /** Per-object permissions, checked where the owning domain loads the object. */
  case ObjectAccess(enforcedIn: String)
}

object Policy {
  val key: AttributeKey[Policy] = AttributeKey[Policy]
}

    // slice/common/api/ProjectAdminGrant.scala
/** An authenticated caller not yet authorized for any project; handlers cannot read the user out of it. */
final class ProjectCandidate private[api] (private[api] val user: User)

/** Proof that `user` passed the ProjectAdmin rule for `project`; only AuthorizationRestService issues it. */
final case class ProjectAdminGrant private[api] (user: User, project: KnoraProject)

    // AdminListRestService, after migration: the user is unreachable until the PDP has decided.
def deleteListNodeComments(candidate: ProjectCandidate)(iri: ListIri): Task[ListNodeCommentsDeleteResponseADM] =
  for {
    project <- listsResponder.projectOfNode(iri)
    grant   <- auth.authorizeProjectAdmin(candidate, project)
    result  <- listsResponder.deleteListNodeCommentsADM(grant, iri)
  } yield result

    ProjectAdmin and ProjectMember keep the existing semantics of isSystemOrProjectAdmin and isProjectMember. SystemAdmin is included. The active-user check applies to every non-Public policy, as in checkActiveUser.

    Alternative Approaches Considered

    • External policy engine (Cedar via cedar-java, OPA, Oso, OpenFGA/SpiceDB): rejected, see above. Cedar would also add a native library to the Bazel multi-arch images. Revisit only if policies must become data that non-developers edit.
    • Enforce every policy in the security logic: impossible for project-scoped policies. The project often comes from the body (DEV-7714) or from a list node, and the body is decoded after the security logic.
    • Proof types on every service method now: strongest guarantee, but it touches about 120 signatures. The pilot proves the shape on two slices first.
    • Two plans, fixes shipped first: recommended in planning. The owner chose one plan. See Risks.

    Technical Considerations

    • What the types guarantee, and what they do not (stated in the ADR):
      • On a migrated endpoint, forgetting the project check does not compile. The security output is a ProjectCandidate, not a User, and the domain write accepts only a ProjectAdminGrant.
      • Checking the wrong project still compiles: for example, the grant is resolved from a body field while the write targets a node in another project. Two things close that. First, the domain write takes the target from the grant (grant.project) wherever the target is the project itself. Second, where the target is an object inside the project (a list node), the responder asserts that the object belongs to grant.project and fails with 403 otherwise. The matrix test, with hand-written expectations as an independent oracle, covers the rest.
      • Unmigrated endpoints keep the hand-called ensure*. The ratchet tracks them until they move.
      • The remaining gaps are bypass routes into the domain: SystemUser (lint allow-list) and object-level ObjectAccess (owning domain).
    • Attribute survival: the policy must be readable from ZServerEndpoint.endpoint after zServerSecurityLogic and serverLogic. NegotiatesOwnAccept.isSet(ep: AnyEndpoint) is the precedent, and it already survives: it is set after bearerSystemAdminEndpoint(...) (SparqlPassthroughEndpoints.scala:119) and read in the server interceptor (DspApiServer.scala). Set the attribute inside the BaseEndpoints factory. Two hazards stay: a later .attribute(Policy.key, x) in a slice silently relabels the endpoint (the Phase 14 table-vs-policy assertion catches it), and withInfo replaces all attributes (unused in modules/webapi/src/main today; REVIEW.md item).
    • Type-level access: private[api] covers org.knora.webapi.slice.common.api and all its subpackages. For final case class ProjectAdminGrant private[api] (...), Scala 3 restricts apply and copy to that access; unapply and the fields stay public, which is deliberate: after authorization, responders read grant.user and grant.project. ProjectCandidate stays a plain final class, because a case class would let unapply leak the user. Package access stops accident, not intent: any file that declares the package gets in, which is also how tests obtain a candidate (Phase 9).
    • Description drift: tapir's .description(...) replaces rather than appends, so a factory cannot inject the text. Instead, Policy.requirement: String renders the sentence (e.g. "Requires SystemAdmin or ProjectAdmin permissions for the list's project."). The ratchet test asserts that every endpoint with a policy has a description containing it, so the prose cannot drift from the attribute again.
    • Status code changes: DEV-7713 and DEV-7714 move from 200 to 403; the ingest report moves from 202 to 401 (its Unauthorized problem type). DEV-7712 moves from 200 to 403 for hidden resources, and from 403 to 200 for project history (measured in Phase 3; checkResourceIris refuses before .resources.head). Anonymous resource creation is refused earlier. DEV-7723 moves value deletion on a hidden resource from 400/404 to 403, and on a visible resource with a hidden value from 403 to 404. All are breaking for a caller that relied on the hole, so the PR description and release notes list them.
    • DEV-7712 decisions:
      • A hidden resource answers 403, consistent with GET /v2/resources (ResourceMessagesV2.toResource).
      • Project history skips forbidden resources silently. This is documented in docs/03-endpoints/api-v2/reading-and-searching-resources.md.
      • Value-level history entries for values the caller cannot see stay unfiltered in this plan. That needs per-version value permissions and is a follow-up (DEV-7720).
    • SystemUser allow-list: the main-source files that use SystemUser in code (10 after the final review; comment mentions do not count) are allow-listed as they are. The lint stops new files, not existing uses. The legitimate prefetch-then-check pattern (ValuesResponderV2:152,818, ValuesRestService:114, ReadResourcesServiceLive:267) stays. Phase 3 removed the last SystemUser reference from ResourcesResponderV2, so it is not on the list.
    • Ingest is a separate release artifact with its own scope-based authorization (AuthorizationHandler). Its commit uses the fix(ingest): scope. AuthorizationHandlerLive.Empty (with JWT_DISABLE_AUTH) stays a no-op.
    • Grant callers: the only non-test callers of ListsResponder.deleteListNodeCommentsADM and StandoffResponderV2.createMappingV2 are the REST paths. The test-it specs (ListsResponderSpec, StandoffResponderV2Spec) obtain a grant through AuthorizationRestService, the same as production. They sit outside slice.common.api and cannot construct a ProjectCandidate, so a test-source helper declared in package org.knora.webapi.slice.common.api (TestCandidates.of(user), in both webapi test and test-it sources) provides one. No Grant.system escape hatch is added to main sources.
    • SystemUser and grants: isSystemAdminOrUser (AuthorizationRestService.scala:120) lets SystemUser through authorizeProjectAdmin. It cannot arrive over HTTP: AuthenticatorLive.ensureActiveUser rejects every built-in user. In-process callers holding SystemUser are what the Phase 11 allow-list tracks.
    • Existence answers before authorization: ensureUserIsAdminOrProjectOwner resolves the node's project before it checks the role (ListsResponder.scala:732-733), so a missing node answers 400 before the 403. Accepted: list nodes are publicly readable (getListsByIri is public), so their existence is no secret. Phases 12 and 13 keep this order. Path and query decode errors also answer before authentication, which is tapir's order.

    Phase 6: DEV-7723 value deletion checks permission before revealing value details

    canRemoveValue (ValuesResponderV2.scala:1144) loads the resource as SystemUser, then answers 400/404 for a wrong resource class, a value not on the resource, or a wrong value type, all before checkValuePermission. Any logged-in user can probe a hidden resource's class and its values' IRIs and types through POST /v2/values/delete. Erase is SystemAdmin-only (ValuesRestService.eraseValue), so only delete is exposed, but erase shares canRemoveValue and must keep working.

    Decisions:

    • A hidden resource answers 403 for every variant of the request, consistent with GET /v2/resources and the DEV-7712 decision above. A missing resource stays 404, so resource existence remains observable, as it is on every v2 read route; a uniform 404 for hidden resources would be a platform-wide change and is out of scope.
    • Within one resource, the answer must not depend on the class, value or type in the request. The 403 message (ResourceUtilV2.scala:54) embeds the caller's email and the resource IRI, which are the same across variants, so the tests compare status and full message per resource.
    • The checks before the resource load (property lookup, link-property rejection, HasStandoffLinkToValue) read only the ontology and leak no data; they stay first.

    • Add e2e tests to ValuesEndpointsE2ESpec for POST /v2/values/delete on the hidden resource, as anythingUser1 and as normalUser: the correct request, a wrong resource class, a non-existent value IRI and a wrong value type each answer 403 with the same message; none names the class or the value type.

    • Add an e2e test as anythingUser2 on a-thing-with-text-values: deleting values/1 and deleting a non-existent value IRI answer the same 404 and message apart from the value IRI.

    Phase 7: DEV-7721 and DEV-7722 admin checks on custom permissions, behind one shared helper

    Three sites decide whether a caller may set custom permissions higher than the defaults, each with its own copy of the "SystemAdmin or ProjectAdmin is exempt" rule. Two copies are wrong:

    • DEV-7721: ValuesResponderV2.scala:268 calls userPermissions.isProjectAdmin(requestingUser.id) with the user IRI, through the String overload (PermissionsMessagesADM.scala:282), so it is always false.
    • DEV-7722: CreateResourceV2Handler.scala:359-361 tests !(isProjectAdmin && !isSystemAdmin), which is !isProjectAdmin || isSystemAdmin. The intended test is !(isProjectAdmin || isSystemAdmin).
    • Correct copy: CreateResourceV2Handler.scala:723-725 (values in a new resource).

    Both bugs are masked today, so they cannot be shown over HTTP with the test data. comparePermissionsADM evaluates both literals through getUserPermissionADM (PermissionUtilADM.scala:87-130, :175-209), which gives SystemUser, SystemAdmin and every holder of ProjectAdminAllPermission the maximum permission on both sides, so they always compare equal. It also evaluates both literals with the caller as creator, and the anything default (the only anything DOAP, permissions-data.ttl) grants CR knora-admin:Creator, the maximum, so no custom literal exceeds it for any caller. DEV-7722 is therefore unreachable: a SystemAdmin is always short-circuited. DEV-7721 shows only for a member of the ProjectAdmin group who lacks ProjectAdminAllPermission, under a default that gives the creator less than the custom literal. New projects give the ProjectAdmin group ProjectAdminAllPermission (PermissionsResponder.scala:546-551), so that needs edited admin permissions; production data is unchecked. The fixes stay, because the wrong checks become live the moment either condition changes, but the proof moves to unit tests with hand-built users and literals. The e2e and test-it checks are regression checks, not red/green.

    One helper replaces all three copies. It takes a typed ProjectIri and uses User.isProjectAdmin(ProjectIri) (User.scala:135), which has no String overload, so passing a user IRI no longer compiles. It keeps today's exemption, User.isSystemAdmin (same answer as PermissionsDataADM.isSystemAdmin) or User.isProjectAdmin(project). It does not add SystemUser, which getUserPermissionADM already treats as maximum.

    // PermissionUtilADM (object), next to comparePermissionsADM
def ensureWithinDefaultPermissions(
  project: ProjectIri,
  customPermissions: String,
  defaultPermissions: String,
  requestingUser: User,
  message: String,
): IO[ForbiddenException, Unit]

    defaultPermissions is a plain String: site 723 passes defaultPropertyPermissions(propertyIri), a map built over exactly the request's properties (CreateResourceV2Handler.scala:208) and already read unguarded at :762, so evaluating it for admins is safe. comparePermissionsADM takes entityProject: IRI, so the helper passes project.value.
