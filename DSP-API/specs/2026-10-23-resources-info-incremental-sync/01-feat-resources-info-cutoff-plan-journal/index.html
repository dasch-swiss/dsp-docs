    Closeout

    • root_cause: GET /v2/resources/info could only list every resource of one class, so an external sync client (MLS, 0807) had to call it once per class and download everything each time to find what changed.
    • investigation: stage timings on 0807 (42k resources) showed a project-wide scan with a date filter costs ~0.8–0.9 s and a full listing 4–5 s; GRAPH scoping and pattern order (type-first vs project-first) made no difference; the stamp-before-commit race and idle-period stall of "newest date seen" led to inclusive cutoffs plus a server asOf; client-supplied creation dates were found to stamp lastModificationDate, so back-dated writes are a documented gap.
    • solution: one sparql"..." template (GetResourceInfoQuery) with optional VALUES class and a trailing COALESCE(lastModificationDate, creationDate) >= cutoff filter; typed row mapping; optional IriDto class and Instant cutoff on the endpoint; resourceClass per entry and asOf per response; docs with a polling protocol.
    • prevention: golden spec for all four query shapes, repo-mapping and rest-service specs (boundary, fallback, ties, fail-fast), and ResourcesInfoE2ESpec against Fuseki that fails if >= becomes >; three review rounds converged.
