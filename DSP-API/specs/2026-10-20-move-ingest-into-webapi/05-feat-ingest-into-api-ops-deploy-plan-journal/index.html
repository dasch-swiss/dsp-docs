    Side findings

    • The plan says compose accepts a byte integer for deploy.resources.limits.memory; docker compose config rejects it ("must be a string"), so the rendered value is quoted (3de88cba).
    • Between Phase 1 and Phase 2 the router {{ STACK }}-ingest is defined by both the api service (DSP_svc) and the still-present ingest service (DSP_iiif) with different services; Traefik drops a router defined twice with different configs. Harmless as long as both phases ship in one PR (H1), but a Phase-1-only deploy would lose ingest.<domain>.

    • The interim iiif ingest service reads the renamed DSP_API_INGEST_MEMORY (3de88cba) so every commit renders; Phase 2 deletes that service.

    • just lint dsp-deploy fails on origin/main (c4d9d52e) with 239 pre-existing violations (var-naming on every upper-case variable, fqcn, risky-file-permissions, also in dsp-setup and inspect-stacks), and no CI job runs it. Phase 1 holds it as "no violation beyond those on base" instead.

    • Phase 1 review (consistency, simplicity, dune, devops, security; 0 fix rounds). All four lenses that saw it flagged the {{ STACK }}-ingest router-name collision with the iiif ingest service (above): it is transient and only matters for a Phase-1-only deploy, so it stays. Phase 2 removes the iiif router; ship and deploy both phases together (H1). Not fixed by renaming because the plan names the router.
    • Review: the api limit plus the old ingest limit are both live until Phase 2, which over-commits memory only in a Phase-1-only deploy. The api-ingest and api-from-app routers tie at priority 100; both have no middleware and target the same service, so the tie is harmless.
    • Review, for dsp-api, not ops-deploy: check that the in-process /ingest/ routes accept Bearer tokens only (the api sets a cookie domain, so cookie auth would make ingest endpoints CSRF-able). Also check that they enforce the KNORA_WEBAPI_DSP_INGEST_AUDIENCE audience.
    • Review suggestions not taken: compute the derived memory byte values once in defaults; mark the DSP_INGEST_* variables the api still uses (mount paths, DSP_INGEST_TMP_DIR, DSP_INGEST_INGEST_BULK_MAX_PARALLEL) as shared, so a Phase 2 cleanup keeps them; drop the duplicate memory comment in defaults.
    • Phase 2 review (consistency, simplicity, dune, devops; 0 fix rounds). Checked: no reference to a removed variable, volume or the iiif ingest service remains outside maintenance/migrations/; the restore expect still matches; the deploy's old-Makefile make down removes DSP_iiif first, so no orphan DSP_iiif_ingest service is left (a consistency concern about orphans was refuted by the devops lens and the plan's deploy mechanics).
    • Review suggestions not taken: guard the INFRA-1404/1413 playbooks with an early fail instead of the header note (the plan asks for a note only); ingest-rsync and make ingest-purge depend on DSP_svc_ingest-* existing (NFS hosts after a DSP_svc deploy; a missing named volume is silently created empty), the same limitation the DSP_iiif_ingest-* names had; the DSP_INGEST_* / DSP_API_INGEST_MEMORY names now configure the api service and could say so; the jenkins ingest_version badge is stale (out of scope per plan).
