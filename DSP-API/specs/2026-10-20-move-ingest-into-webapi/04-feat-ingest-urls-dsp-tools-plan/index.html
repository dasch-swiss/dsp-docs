    feat: dsp-tools reaches ingest under /ingest/ on the API host

    Overview

    dsp-tools stops talking to a separate ingest server. Every ingest call goes to <server>/ingest/... on the API host, with the paths after the prefix unchanged. start-stack and the e2e testcontainers no longer run the daschswiss/dsp-ingest container or its SQLite database. The API container serves ingest instead and gets ingest's storage settings and volumes.

    The PR is opened as part of this work but merged only once prod serves /ingest/ (PRD constraint). Older dsp-tools releases keep working through the permanent ingest.<domain> proxy, so this release needs no fallback.

    Problem Statement / Motivation

    The PRD moves dsp-ingest into dsp-api under /ingest/ and stops publishing the standalone dsp-ingest image (REQ-4.5). dsp-tools currently:

    • derives the ingest URL as https://ingest.<domain> remotely and http://0.0.0.0:3340 locally;
    • runs daschswiss/dsp-ingest:${API} in start-stack and in the e2e testcontainers, with DB_JDBC_URL and an ingest-db volume.

    Once a dsp-api release ships without the ingest image, start-stack and the e2e suite on that version can't start. The remote ingest.<domain> host keeps working through the proxy, but the PRD's goal is that DaSCH clients use one address.

    Proposed Solution

    The base URL is the only thing that changes. All three ingest clients build their URLs as f"{dsp_ingest_url}/projects/...", so pointing dsp_ingest_url at <server>/ingest moves every call without touching the client code:

    Call site (origin/main) Path after the base URL (unchanged)
    src/dsp_tools/clients/ingest.py:98 (DspIngestClientLive._ingest) /projects/{sc}/assets/ingest/{filename}
    src/dsp_tools/clients/bulk_ingest_client.py:110 /projects/{sc}/bulk-ingest/ingest/{file}
    src/dsp_tools/clients/bulk_ingest_client.py:114 /projects/{sc}/bulk-ingest
    src/dsp_tools/clients/bulk_ingest_client.py:160 /projects/{sc}/bulk-ingest/mapping.csv
    src/dsp_tools/cli/utils.py:110 (_check_ingest_health) /health

    URL derivation. get_canonical_server_and_dsp_ingest_url (src/dsp_tools/cli/utils.py:128) derives the ingest URL from the canonical server, as f"{server}/ingest":

    Input Server Ingest URL (new)
    localhost:3333, 0.0.0.0:3333 http://0.0.0.0:3333 http://0.0.0.0:3333/ingest
    admin./app./api./ingest./bare <x>.dasch.swiss https://api.<x>.dasch.swiss https://api.<x>.dasch.swiss/ingest

    The default_dsp_ingest_url parameter goes away (here and in entry_point._derive_dsp_ingest_url), since the ingest URL is no longer independent of the server. ingest.<x>.dasch.swiss stays accepted as input and is canonicalised to the API host like the other subdomains.

    # src/dsp_tools/cli/utils.py (sketch)
LOCALHOST_API = "http://0.0.0.0:3333"
LOCALHOST_INGEST = f"{LOCALHOST_API}/ingest"

def get_canonical_server_and_dsp_ingest_url(
    server: str, default_dsp_api_url: str = LOCALHOST_API
) -> tuple[str, str]:
    ...
    if localhost_match:
        server = default_dsp_api_url
    elif remote_url_match:
        server = f"https://api.{remote_url_match.group(1)}.swiss"
    else:
        raise CliUserError(f"Invalid DSP server URL '{server}'")
    dsp_ingest_url = f"{server}/ingest"
    ...

    Explicit ingest URL. No --dsp-ingest-url CLI flag exists on origin/main: _derive_dsp_ingest_url always overwrites parsed_arguments.dsp_ingest_url. The decision is to add no flag. The programmatic override stays: ServerCredentials.dsp_ingest_url and NetworkRequirements.ingest_url remain separate fields, so a caller that builds ServerCredentials itself (tests, library use) can still point ingest anywhere, including at the old ingest.<domain> proxy. The ServerCredentials.dsp_ingest_url default becomes http://0.0.0.0:3333/ingest.

    Health check. Keep the separate ingest health check, now at <server>/ingest/health (REQ-2.4/REQ-1.2 keep /health on the ingest slice). Against a dsp-api that predates the move, it fails fast with IngestNotReachableError instead of failing mid-upload. That error's local message, which tells the user to check "the ingest container", now says that the local DSP-API must be a version that serves /ingest/ and suggests restarting with dsp-tools start-stack.

    start-stack. The ingest service, its ingest-db volume and port 3340 are removed from docker-compose.yml, docker-compose.override.yml and docker-compose.override-host.j2. The api service takes over ingest's storage settings and volumes (see start-stack api service below). The dsp-app config files point ingestUrl at http://<host>:3333/ingest.

    e2e testcontainers. The ingest testcontainer, its port, its name, its image version and its ingest_db artifact dir are removed. The API testcontainer gets the same ingest settings and volumes as the start-stack api service, and creds points at http://0.0.0.0:{ports.api}/ingest.

    start-stack api service

    This follows the dsp-api plan's cross-repo contract. dsp-api reads ingest's settings from its own ingest.conf under an INGEST_ prefix (REQ-4.1); the old unprefixed ingest variables are ignored, and unprefixed ALLOW_ERASE_PROJECTS drives only dsp-api's own erase flag.

      api:
    image: daschswiss/knora-api:${API}   # API = a dsp-api release that serves /ingest/ (see H1, H2)
    depends_on: [sipi, db]
    ports:
      - "3333:3333"                       # 3340 is gone; ingest is under :3333/ingest
    volumes:
      - ./sipi/images:/opt/images         # read-write: ingest writes assets here; sipi reads the same host dir
      - ./sipi/tmp-dsp-ingest:/opt/temp    # ingest temp dir; bulk ingest reads <temp>/import/<shortcode>
    environment:
      # ...existing KNORA_WEBAPI_* settings unchanged, except:
      # removed: KNORA_WEBAPI_DSP_INGEST_BASE_URL=http://ingest:3340   (dsp-api no longer reads it)
      - KNORA_WEBAPI_DSP_INGEST_AUDIENCE=http://localhost:3340       # unchanged; dsp-api mints and checks it
      - INGEST_STORAGE_ASSET_DIR=/opt/images
      - INGEST_STORAGE_TEMP_DIR=/opt/temp
      - INGEST_ALLOW_ERASE_PROJECTS=true  # ingest-side erase gate (ingest container set ALLOW_ERASE_PROJECTS)
      - ALLOW_ERASE_PROJECTS=true         # already set on api today; drives dsp-api's own flag only
      # INGEST_SIPI_USE_LOCAL_DEV is left unset (default false): the Sipi CLI shipped in the api image is used

    Dropped with the ingest container: SERVICE_HOST, SERVICE_PORT, SERVICE_LOG_FORMAT, JWT_AUDIENCE, JWT_ISSUER, JWT_SECRET (dsp-api's own authentication applies), DB_JDBC_URL, DSP_API_URL, STORAGE_*, SIPI_USE_LOCAL_DEV, and the custom-host JWT_ISSUER override. KNORA_WEBAPI_DSP_INGEST_ASSET_DIR and KNORA_WEBAPI_DSP_INGEST_EXTERNAL_BASE_URL are not set either: dsp-api removes them and reads the asset directory from INGEST_STORAGE_ASSET_DIR. INGEST_BULK_MAX_PARALLEL and INGEST_EXECUTOR_CPU_SHARE (default 0.5) keep their defaults. The host directories ./sipi/images and ./sipi/tmp-dsp-ingest keep their current paths in ~/.dsp-tools/start-stack, so a running user's existing assets stay where they are. No memory limit is set in start-stack today, and none is added.

    Technical Considerations

    • Filename built from the ingest URL. UploadFailures.execute_error_protocol (src/dsp_tools/commands/ingest_xmlupload/upload_files/upload_failures.py:43) strips the scheme from dsp_ingest_url and puts the rest into a CSV filename. With api.dasch.swiss/ingest, the / makes Path("upload_failures_0001_api.dasch.swiss/ingest.csv") point into a directory that doesn't exist, and the write fails exactly when more than maximum_prints uploads have failed. The / has to be replaced (e.g. by _) before the URL goes into the filename. This is the one behavioural change the new base URL forces outside the CLI layer.
    • Uploads send Content-Length. dsp-api buffers chunked request bodies and answers 413 to a chunked upload over 1 MiB. Both upload paths (DspIngestClientLive._ingest, BulkIngestClient.upload_file) pass an open file object as data= to requests, which sets Content-Length from the file size, so no change is needed. Phase 2's manual run and Phase 3's e2e uploads exercise it with files above 1 MiB.
    • Client code is unchanged. DspIngestClientLive, BulkIngestClient and resume_xmlupload take the base URL from creds.dsp_ingest_url and need no edit. test/unittests/clients/test_bulk_ingest_client.py uses DSP_INGEST_URL = "https://example.com"; changing it to https://example.com/ingest makes the tests show the prefix is carried through.
    • versions.env sequencing. versions.env drives the start-stack images, the e2e images (_get_image_versions) and the dsp-api ref from which sipi.docker-config.lua is downloaded. The first dsp-api release without the ingest image breaks today's compose (it still references daschswiss/dsp-ingest:${API}). The automated bump PR for that release would therefore go red, and only this PR makes it green. This PR sets API/DB itself to a dsp-api release tag that serves /ingest/ (a real git tag, since the e2e setup and _get_url_prefix fetch files from raw.githubusercontent.com/dasch-swiss/dsp-api/<tag>/). At merge time, the tag is moved to the release prod runs (H2).
    • dsp-app config. The ingestUrl in dsp-app-config.json gains a path (/ingest). The APP version in versions.env must be a dsp-app release that accepts a path in ingestUrl (the dsp-app part of this PRD).
    • Repo rule on test edits. dsp-tools' CLAUDE.md asks for confirmation before adjusting a test. The test edits listed in this plan (expected URLs, the testcontainer layout, the start-stack override assertions) are approved by this plan. Any other test change still needs that confirmation.
    • Conventions. src/dsp_tools/cli/** follows src/dsp_tools/cli/CLAUDE.md, and src/dsp_tools/commands/ingest_xmlupload/upload_files/** follows its own CLAUDE.md (per eng.yaml). Commits and the PR title follow Conventional Commits (CONVENTIONS.md), e.g. feat: reach ingest under /ingest/ on the API host.

    Acceptance Criteria

    • For every supported server input, dsp-tools derives the ingest URL <canonical server>/ingest; ingest.<x>.dasch.swiss as input still resolves to https://api.<x>.dasch.swiss and https://api.<x>.dasch.swiss/ingest

    • More than maximum_prints upload failures against an /ingest URL write the failure CSV to a single file in the working directory
    • start-stack starts no ingest container, uses no DB_JDBC_URL/ingest-db volume, and an ingest-xmlupload against it succeeds
    • The e2e suite runs with three containers (fuseki, sipi, api) and passes
    • No 3340, dsp-ingest image or ingest.<domain> derivation remains in src/ or test/ (git grep -n -E "3340|daschswiss/dsp-ingest|DB_JDBC_URL" -- src test returns nothing)
    • just unittests, just integration-tests, just e2e-tests and just lint pass

    Dependencies & Risks

    • dsp-api must ship first (H1). Phases 2 and 3 need a tagged dsp-api release whose knora-api image serves /ingest/, includes the Sipi CLI, ffmpeg and ffprobe, and starts without any ingest database setting. Phase 1 can be built and unit-tested before then.
    • Env var contract (dsp-api plan). Phases 2 and 3 use the names the dsp-api plan fixes: INGEST_STORAGE_*, INGEST_ALLOW_ERASE_PROJECTS, kept KNORA_WEBAPI_DSP_INGEST_AUDIENCE, no KNORA_WEBAPI_DSP_INGEST_* base URL or asset dir. If the API container still carried the old unprefixed names, dsp-api would silently ignore them and ingest would fall back to its defaults (/opt/images, /opt/temp), so the temp mount path /opt/temp must be passed through INGEST_STORAGE_TEMP_DIR. INGEST_SIPI_USE_LOCAL_DEV stays unset, so the image's bundled Sipi CLI, ffmpeg and ffprobe are used.
    • Bump-PR timing. Between the dsp-api release without the ingest image and this PR's merge, the automated bump-stack-versions PR for that release fails e2e and can't auto-merge. Released dsp-tools versions keep pulling the older pinned images from their own versions.env, so they are unaffected. Only main's bump is held back, which H2 resolves.
    • Older dsp-tools releases. They use https://ingest.<domain> and http://0.0.0.0:3340. Remote use keeps working through the permanent proxy. Local start-stack of an old release keeps working because it pins its own older images. No fallback is added in this release.
    • dsp-app ingestUrl with a path. If the pinned APP release builds ingest URLs in a way that drops the /ingest path, uploads from the local dsp-app break. H1 picks a dsp-app release from the dsp-app part of the PRD.
    • Custom host. With --custom-host, ingest is reached through the API's external host and port; there's no separate ingest issuer to override any more. Phase 2's manual check covers the default host only. The custom-host template change is reviewed but not run.
