    feat: Ingest runs inside dsp-api under /ingest/

    Revisions

    • 2026-10-27, owner decision: minimal diff; the structure under modules/ingest is not touched. The previous shape moved 67 files into modules/webapi/.../slice/ingest/ with package renames, rebuilt the HTTP layer as new Ingest*Endpoints/*ServerEndpoints/*RestService files with re-ported specs, copied test helpers and binary fixtures, and kept the standalone module alive by making it depend on webapi (+11k/−7.5k without rename detection). It is rejected for diff size (see Alternative Approaches Considered) and preserved on branch backup/docs/move-ingest-into-webapi-brief (tip 11c2df207). Phase 1 (done) is unchanged; Phases 2 and later are rewritten. Cross-repo contracts are unchanged, except that the size and MIME-type backfills stay main classes instead of becoming maintenance actions.

    Overview

    modules/ingest (package swiss.dasch) stays where it is, with its file layout, and becomes a library that //modules/webapi depends on. dsp-api serves ingest's existing tapir server endpoints under /ingest/ with ingest's own error bodies, token check, scopes and value types. Ingest reads its own ingest.conf (INGEST_* variables) and gets dsp-api's JWT secret, issuer and ingest audience from webapi. Ingest's permission callback and dsp-api's DspIngestClient become in-process calls. Child processes are the OOM killer's first choice and run under a bounded number of permits, and ingest request handling runs on a dedicated executor. The SQLite database (Phase 1), the standalone Main, HTTP server, image, publishing and local-stack container go.

    This plan covers dsp-api only. The proxy, deployment and client changes are separate plans in ops-deploy, dsp-app and dsp-tools (see Dependencies & Risks).

    Problem Statement / Motivation

    See the PRD. In short: two services to build, deploy, configure and monitor, two token validators, a second public address for clients, and a SQLite database that nothing reads to decide behaviour. dsp-api already reaches into ingest's code (//modules/webapi depends on //modules/ingest:ingest_classes for AssetInfoService) and over HTTP (DspIngestClient), and ingest calls back into dsp-api over HTTP (FetchAssetPermissions -> GET /admin/files/...). The split costs more than it isolates.

    Proposed Solution

    1. SQLite goes first, in the standalone module (Phase 1, done).
    2. Ingest is a library; webapi mounts its server endpoints. Ingest's handlers already expose List[ZServerEndpoint[Any, ZioStreams]] (api/*EndpointsHandler.scala), the type webapi's slice/api/Endpoints.scala aggregates. A new webapi IngestServerEndpoints takes the four handlers and maps each endpoint with tapir's ServerEndpoint.prependSecurityIn("ingest"), so the routes, inputs, outputs, error bodies and docs are ingest's own. Ingest's RequiresMethod bases already force a method on every endpoint.
    3. Auth keeps ingest's acceptance rule. Ingest's AuthServiceLive and AuthorizationHandlerLive are reused as they are. Webapi provides their Configuration.JwtConfig from app.jwt (secret, issuer) and app.dsp-ingest.audience, with disableAuth = false. Scope refusals stay 401 with the standalone bodies, logged-out tokens stay accepted (ingest never consulted webapi's logout cache), and /ingest/metrics stays public.
    4. Permission check in-process. Ingest's FetchAssetPermissions trait stays in ingest; its HTTP FetchAssetPermissionsLive is deleted. Webapi implements the trait over AssetPermissionsCache and Authenticator (ADR-0011: the consumer defines the port, the provider's side implements it; no dependency cycle).
    5. Separate configuration. modules/ingest/src/main/resources/application.conf becomes ingest.conf (root ingest), read by ingest's own Configuration.layer with ConfigFactory.parseResources("ingest.conf"). The service, jwt and dsp-api blocks go. webapi keeps ConfigFactory.load(), which never reads ingest.conf, so no key or variable is read by both. Every ingest variable gets the INGEST_ prefix (see the mapping table).
    6. DspIngestClient in-process. The trait and its four consumers stay. DspIngestClientLive is rewritten in place over ingest's AssetInfoService, ProjectService and ImportService, keeping the HTTP client's behaviour: not-found export is None, import failures are logged only, erase is gated by ingest's allow-erase-projects.
    7. Contained workload, smallest form. A small IngestExecutor in ingest (swiss.dasch.infrastructure) owns a fixed pool of max(1, floor(availableProcessors * cpu-share)) threads and a semaphore with as many permits. CommandExecutorLive.execute takes a permit and, outside local-dev mode, starts the process through /bin/sh -c 'echo 1000 > /proc/self/oom_score_adj && exec "$0" "$@"'. IngestServerEndpoints runs the logic of every ingest endpoint except info, health and metrics onExecutor that pool; forked jobs inherit it.
    8. Image and removal. The dsp-api image layers //modules/sipi:runtime_fs_{amd64,arm64} (it already runs as root). The standalone Main, server wiring, app binary, image, publishing, modules/test-ingest-integration, the testkit ingest container, the compose service, just recipes and CI job go.

    Alternative Approaches Considered

    • Move ingest into a webapi slice and rebuild its API layer (the shape before 2026-10-27): git mv the domain into slice/ingest/ with package renames, rebuild the HTTP layer on webapi's three-tier split with webapi's Scope, an OriginalAccess port, ported endpoint specs, copied test helpers and fixtures, and backfills as maintenance actions. Rejected for diff size (+11k/−7.5k without rename detection) and review cost; the gain was layout conformance, not behaviour. Preserved on backup/docs/move-ingest-into-webapi-brief.
    • Use webapi's securedEndpoint and User for ingest routes. Rejected: it resolves a User from the subject, accepts HTTP basic and consults the logout cache, so it would reject tokens ingest accepts (e.g. the service token from JwtService.createJwtForDspIngest, whose subject is the issuer) and change error bodies (REQ-1.2, REQ-1.3).
    • Unify ingest's refined value types with webapi's (ProjectShortcode vs KnoraProject.Shortcode etc.). Rejected: their decode-failure messages appear in 400 bodies (REQ-1.2).
    • Top-level ingest { } block inside webapi's application.conf. Workable, but ingest.conf keeps the file in the ingest module and makes the "no shared key" rule visible in the layout.
    • Prefix the paths inside ingest's BaseEndpoints. Equally small, but it changes ingest's own specs' URLs; prependSecurityIn at registration leaves ingest untouched.

    Technical Considerations

    • Module layout. Unchanged under modules/ingest/src/{main,test}. Webapi-side code is two files in slice/ingest/ (IngestServerEndpoints, IngestModule), the permission adapter in slice/admin/domain/service/ and the rewritten DspIngestClientLive in place. //modules/webapi depends on //modules/ingest; the ingest_classes target goes, because :ingest then carries only ingest.conf (no application.conf, no logback.xml) and no longer collides with webapi's resources.
    • Layer wiring. IngestModule is one ZLayer.makeSome over the ingest layers Main used to list, exposing only IngestServerEndpoints, AssetInfoService (replacing store/iiif/impl/AssetInfoServiceLayer.scala) and DspIngestClient. Ingest types never reach LayersLive's environment, so name clashes (BaseEndpoints, Features, JwtConfig) do not matter. Its inputs are AppConfig, PrometheusPublisher, AssetPermissionsCache, Authenticator and ingest's configuration, which LayersLive.remainingLayer takes as a parameter (default ingest's Configuration.layer) so the testkit can pass its own.
    • Error envelope. Ingest's ApiProblem outputs stay on ingest's BaseEndpoints. Nothing is added to webapi's BaseEndpoints.errorOutputs.
    • Security input. Bearer only, as before; that keeps the routes CSRF-safe under webapi's credentialed, reflected-origin CORS.
    • Body buffering. webapi runs RequestStreaming.Hybrid(1 MiB) (core/DspApiServer.scala): bodies with a declared Content-Length above 1 MiB stream; smaller bodies and every chunked body are aggregated before tapir runs, for any caller, and a chunked body over the threshold gets a bare 413. See dasch-specs/learnings/design-decisions/security-logic-authenticates-body-buffering-precedes-it.md.
    • Executor scope. onExecutor wraps the server logic, not the security logic, of every ingest endpoint except info, health and metrics, and the export, import and erase methods of DspIngestClientLive. Forked daemon fibers (bulk ingest, maintenance actions, asset-overview report) inherit the executor; a spec asserts it. Checksums run on the calling fiber, so they stay on the pool. BagIt zip and unzip use attemptBlocking, so they take a permit themselves (owner, 2026-10-27). Permit sections are leaf-level: CommandExecutorLive.execute and the two BagIt calls take one, and none calls another.
    • Observability. webapi's server span and spanNameInterceptor apply; routes show as GET /ingest/projects/{shortcode}/... (the prefix is part of the security input, which showPathTemplate includes; a spec pins it).
    • Metrics. /ingest/metrics serves the API process's PrometheusPublisher, the same data as :3339/metrics. Ingest's per-endpoint ZioMetrics interceptor is not carried over; webapi's RequestMetrics covers the routes.
    • Info. /ingest/info keeps ingest's BuildInfo (name = "dsp-ingest"), stamped with the same git version and commit as dsp-api.
    • Security review points. The original-download route passes an optional token; an invalid token is anonymous for the endpoint, and the in-process adapter authenticates it with webapi's Authenticator. A failure there answers 500 "error fetching permissions", as it does today when dsp-api returns 401. Erase stays gated by ingest's allow-erase-projects and admin scope.

    Dependencies & Risks

    Cross-repo contracts this plan fixes (the ops-deploy, dsp-app and dsp-tools plans must match):

    • The api container needs INGEST_STORAGE_ASSET_DIR, INGEST_STORAGE_TEMP_DIR (read-write mounts), and optionally INGEST_BULK_MAX_PARALLEL, INGEST_ALLOW_ERASE_PROJECTS, INGEST_EXECUTOR_CPU_SHARE. It must not set INGEST_SIPI_USE_LOCAL_DEV=true. It keeps KNORA_WEBAPI_DSP_INGEST_AUDIENCE and drops KNORA_WEBAPI_DSP_INGEST_BASE_URL, KNORA_WEBAPI_DSP_INGEST_EXTERNAL_BASE_URL and KNORA_WEBAPI_DSP_INGEST_ASSET_DIR. The old unprefixed ingest variables (STORAGE_*, SIPI_USE_LOCAL_DEV, JWT_*, DB_JDBC_URL, DSP_API_URL, SERVICE_*) are ignored. ALLOW_ERASE_PROJECTS still drives dsp-api's own feature flag only.
    • Health: GET /ingest/health on the API port (3333), 200 when healthy. Metrics: GET /ingest/metrics returns the whole API process's metrics, identical to :3339/metrics. Scraping both double-counts.
    • The image runs as root and contains /sbin/sipi, /usr/bin/ffmpeg, /usr/bin/ffprobe, /bin/sh.
    • The proxy forwards ingest.<domain>/<path> to /ingest/<path> unchanged, including Authorization and Content-Length. Uploads without Content-Length over 1 MiB get 413 from dsp-api (see risks).
    • Ingest's Swagger UI (ingest.<domain>/docs) is not carried over; ingest endpoints appear in dsp-api's API docs served by the metrics server.
    • Child processes inherit the api container's environment (scala.sys.process passes it on and the sh -c '… exec "$0" "$@"' wrapper keeps it), so SIPI_SENTRY_* set on api reach the Sipi CLI as they reached it in the ingest container.
    • The size and MIME-type backfills stay main classes (swiss.dasch.MigrateSizes, swiss.dasch.MigrateMimeTypes) on the dsp-api image's classpath (java -cp '/opt/docker/lib/*' ...), reading INGEST_*. The ops-deploy playbooks INFRA-1404/1413 that ran them in the ingest container are not re-run.

    Resolved decisions:

    • 2026-10-27: minimal diff; modules/ingest keeps its structure and package (see Revisions).
    • Scope refusals answer 401 with the standalone bodies; /ingest/metrics stays public; logged-out tokens are still accepted; all three follow from reusing ingest's handlers and AuthService unchanged.
    • In-process importProject keeps the HTTP client's log-only failure handling (Phase 3).
    • The backfills stay scala_binary mains of the library, not maintenance actions.

    Follow-ups (out of scope; name them in the execution's final report):

    • DspIngestClient.importProject now runs in-process, so a failed asset import could fail the project-import request instead of only being logged. Changing it is a behaviour change for project import and needs its own decision.

    Ordering: H1 precedes the ops-deploy cutover; dsp-tools merges its /ingest/ change only once prod serves /ingest/ (PRD constraint). dsp-app may switch once the environment it targets runs this release.

    Open questions (defaults chosen; revisit in plan review):

    • ffmpeg and the Sipi CLI use several threads per process, so permits bound the process count, not cores. Default: no -threads cap (it can change encoder output).

    Chunked uploads (no Content-Length) over 1 MiB get a bare 413 under Hybrid streaming, where the standalone service streamed them M H Phase 3 E2E covers the declared-length case; dsp-app and dsp-tools plans confirm their uploads send Content-Length; documented in Phase 6
    Forked jobs or blocking work escape the ingest executor and compete with API traffic M M Permits around child processes; IngestExecutorSpec asserts executor inheritance for forked fibers; permits around BagIt zip and unzip
