    refactor: add the grant and factory machinery for the remaining project-scoped endpoints (batch 2)

    Overview

    Batch 2 of the migration in 01-refactor-authorization-policy-migration-plan.md. It migrates 63 endpoints. Each needs a piece of new machinery first: ontology request parsing without a user, grants by shortcode, shortname and group, a ProjectMember grant, a public factory that reads the optional user, policies for the FAIR and SPARQL routes, v3 policy factories, and a grant in the v2 ontology responder. Phase numbers run through all three batch plans.

    Problem Statement / Motivation

    The project-scoped endpoints here find their project through a shortcode, a shortname, a group, an ontology or a v3 path. The ontology writes check the project deep in the responder with a re-implemented rule (OntologyCacheHelpers). The remaining endpoints are built outside the standard bases (FAIR, SPARQL passthrough, v3), so no existing factory can declare their policy.

    Proposed Solution

    • Phase 8 splits OntologyV2RequestParser so requests are parsed without a user and completed with grant.user, then migrates ontology creation and deletion.
    • Phases 9-11 add authorizeProjectAdminByShortcode/ByShortname, authorizeProjectAdminOfGroup, and the ProjectMember factory and grant.
    • Phases 12-13 add publicPolicyEndpointWithUser, a publicPolicyEndpoint overload for a caller-supplied error output (FAIR), and a policy on bearerSystemAdminEndpoint.
    • Phases 14-15 build the v3 factories in slice.common.api and migrate v3.
    • Phases 16-17 move the v2 ontology writes to a grant taken by the responder and asserted inside the ontology lock.

    Technical Considerations

    The shared rules live in the main plan (01-refactor-authorization-policy-migration-plan.md): Proposed Solution (the six steps per phase, the code shape and the matrix rule) and Technical Considerations (order of answers, anonymous 401, unknown project, handlers without a User, kept 400s and 404s, domain error channels, SystemUser, package privacy, decision-6 tests, the ontology lock). Every phase applies them; this plan repeats only what is specific to the batch.

    Batch-specific points:

    • Every new PDP method and factory gets unit tests in AuthorizationRestServiceSpec or BaseEndpointsSpec, and the compile-negative test keeps passing. No public way to mint a ProjectCandidate is added.
    • The ontology project is resolved from the cache. An unknown ontology still answers 404, and that check comes before any 403.
    • checkOntologyAndEntityIrisForUpdate keeps its IRI validation. Only its permission part is replaced. The old permission check is deleted in batch 3 (Phase 22), because the can-do endpoints still use it.

    Implementation Phases

    Verification commands are those in CLAUDE.md: just test-unit, just test-e2e, just check, and filtered runs such as bazel test //modules/test-e2e:test --test_filter='.*EndpointPolicyE2ESpec.*'. Every phase that removes baseline lines runs EndpointPolicyE2ESpec, and every phase that adds matrix rows runs AuthorizationMatrixE2ESpec.

    Batch 2: new machinery

    Phase 8: Ontology request parsing without a user, and ontology creation and deletion

    Endpoints (2): POST /v2/ontologies (projectFrom = "body attachedToProject") and DELETE /v2/ontologies/{ontologyIri} (projectFrom = "path ontology's project"). The parser change is the machinery Phases 16 and 17 reuse.

    • OntologyV2RequestParser: each parse method returns the request without the requesting user, and the RestService completes it with grant.user after the grant; the parser tests are adjusted
    • OntologiesEndpoints: both routes use projectAdminPolicyEndpoint
    • OntologiesRestService: both methods take a ProjectCandidate and obtain the grant in place of ensureSystemAdminOrProjectAdminById
    • OntologyResponderV2.createOntology takes the grant and creates in grant.project; any responder-level re-check is removed
    • OntologyResponderV2.deleteOntology takes the grant and asserts, inside the ontology lock, that the ontology belongs to grant.project (403 otherwise); an unknown ontology still answers 404 before any 403
    • Responder test: deleting with a grant for another project answers 403 and deletes nothing
    • Matrix rows for both endpoints (fresh ontology per cell)
    • Baseline: remove the 2 lines and lower baselineSize
    • Run bazel test //modules/test-e2e:test --test_filter='.*(EndpointPolicy|AuthorizationMatrix|Ontolog).*'; it passes
    • Phase review: adversarial review of this phase's commits; verified findings fixed before the next phase starts

    Phase 9: Grants by shortcode and shortname

    Endpoints (11): Appendix A, phase 9.

    • AuthorizationRestServiceSpec: SystemAdmin, ProjectAdmin, other-project admin, member, inactive user and unknown project, for both methods
    • ProjectsEndpoints and ProjectRestService: the 6 shortcode and shortname routes in phase 9 use projectAdminPolicyEndpoint and the new grants
    • ProjectsLegalInfoEndpoints and ProjectsLegalInfoRestService: POST copyright-holders, PUT licenses/{licenseIri}/enable and /disable, and PUT legal-info/resource use projectAdminPolicyEndpoint and the shortcode grant
    • MetadataEndpoints and MetadataRestService: GET /v2/metadata/projects/{projectShortcode}/resources uses projectAdminPolicyEndpoint and the shortcode grant
    • Matrix rows for the 11 endpoints

    • Phase review: adversarial review of this phase's commits; verified findings fixed before the next phase starts

    Phase 10: Group-scoped grant

    • GroupsEndpoints and GroupRestService: PUT /{groupIri}, PUT /{groupIri}/status, DELETE /{groupIri} and GET /{groupIri}/members use projectAdminPolicyEndpoint and the group grant

    Phase 13: Policies for endpoints built outside the standard bases

    • ExportEndpoints: POST /v3/export/resources/oai uses systemAdminPolicy (anonymous now answers 401, was 403; its v3 docs say so); POST /v3/export/resources uses objectAccessPolicy
