    feat: Project-scope the /v2/searchbylabel Lucene lookup via GRAPH <projectDataGraph>

    Recommendation: go

    The dev measurement (Success Metrics below) shows a clear gain, well outside noise. Across 8 project-restricted typeahead cases, the scoped queries are 1.5–8× faster. The worst unscoped case drops from 2.4 s to 0.3–0.5 s, and every count and page is identical scoped and unscoped. The truncation effect the ticket names does not occur at today's hit limit (1,000,000). The gain is purely the removed per-hit work.

    Overview

    /v2/searchbylabel (the typeahead path) runs its Lucene lookup unscoped and applies limitToProject afterwards with an attachedToProject join. These are SearchQueries.selectCountByLabel and SearchQueries.constructSearchByLabel, called from SearchResponderV2Live.searchResourcesByLabelCountV2 and searchResourcesByLabelV2. DEV-7594 fixed the same shape for /v2/search and the Gravsearch text functions (ADR-0012). This plan applies that fix to the label route. When limitToProject is set, the responder resolves the project's data graph through the ProjectDataGraphs port and wraps only the text:query statement in GRAPH <dataGraph> { }, in both queries. The attachedToProject join is dropped. An unknown project answers with an empty result without querying, exactly as /v2/search does.

    Problem Statement / Motivation

    A project-restricted typeahead pays for every matching Lucene hit in the repository before the join discards the other projects' hits. The label lookup's hits are not only resources: rdfs:label, valueHasString and valueHasComment share one Lucene field, so (rdfs:label "Basel*" N) also returns every text value containing "Basel" (docs/development/dsp-api-fuseki-query-execution.md, Fact 10). On dev, "Basel*" has 72,809 hits in 080C and 66,519 in lhtt, while a beol-restricted typeahead keeps 1,612. Typeahead fires once per keystroke, so 2.4 s per request is noticeable in the UI.

    Proposed Solution

    Mirror SearchFulltextQuery exactly:

    1. SearchQueries takes dataGraph: Option[InternalIri] in place of limitToProject: Option[ProjectIri] in both builders. A private labelLookupClause(query, dataGraph) emits either the bare ?resource text:query (rdfs:label $query $luceneHitLimit) . or the same statement inside GRAPH <dataGraph> { }, and is shared by both builders. No attachedToProject is emitted any more: a known project is a data graph, and an unknown one never reaches the builder. The rest of each statement (knora-base:creationDate in the count query, rdfs:label ?label in the page subquery) becomes a separate statement on ?resource outside the GRAPH.
    2. SearchResponderV2Live runs both label queries inside SearchResponderV2Live.withProjectDataGraph(projectDataGraphs, limitToProject, ifUnknown = …). For the count, ifUnknown is ResourceCountV2(0). For the page, it is ReadResourcesSequenceV2(Vector.empty[ReadResourceV2]). Validation (validateSearchString, ensureIsFulltextSearch, the Lucene parse) stays before the lookup, so an invalid term is still a 400 for an unknown project.
    3. The class restriction (?resource a ?resourceClass . ?resourceClass rdfs:subClassOf* <cls> .) stays as it is, outside the GRAPH (DEV-6833).

    Target shape of the scoped count query (page subquery analogous):

    SELECT (count(distinct ?resource) as ?count)
WHERE {
    GRAPH <http://www.knora.org/data/0001/anything> {
        ?resource <http://jena.apache.org/text#query> (rdfs:label "Anton*" 1000000) .
    }
    ?resource knora-base:creationDate ?resourceCreationDate .
    ?resource a ?resourceClass .
    ?resourceClass rdfs:subClassOf* <http://www.knora.org/ontology/0001/anything#Thing> .
    FILTER NOT EXISTS { ?resource knora-base:isDeleted true . }
}

    Code sketch for the shared clause (the same pattern as SearchFulltextQuery.luceneLookupClause):

    private def labelLookupClause(luceneQuery: FusekiLucenceQuery, dataGraph: Option[InternalIri]): Fragment = {
  // `Literal.string` escapes for SPARQL itself, so the raw Lucene query goes in, not `getQueryString`.
  val query  = Literal.string(luceneQuery.value)
  val lookup = sparql"?resource <http://jena.apache.org/text#query> (rdfs:label $query $luceneHitLimit) ."
  dataGraph match {
    case Some(graph) =>
      sparql"""|GRAPH ${Iri.unsafeFrom(graph.value)} {
               |    $lookup
               |}"""
    case None => lookup
  }
}

    Technical Considerations

    • Exactness. A label hit is the resource itself (rdfs:label sits on the resource), so the resources among the scoped hits are exactly those whose label triple is in the project data graph. Dropping attachedToProject relies on the one-graph rule (docs/contexts/resources-values/CONTEXT.md; 0 exceptions on stage, 2026-10-21), as /v2/search already does. Measured: all 8 dev cases return identical counts and pages.
    • List nodes survive the scoped inner page subquery. The lookup returns every labelled subject in the data graph, not only resources: a project's list nodes live in its data graph (docs/contexts/resources-values/CONTEXT.md) and carry rdfs:label, so the page's inner SELECT (which has no resource-ness check) now keeps all of them, where the attachedToProject join kept only root nodes. The outer query's a knora-base:Resource drops them, and http://rdfh.ch/lists/… sorts after every http://rdfh.ch/<shortcode>/…, so pages are unchanged. This is the same IRI-grammar accident the unscoped query already relies on (Fact 10, "Two traps follow"); not a new risk, and DEV-6851 / DEV-6850 remove it. The count query is unaffected (creationDate is on resources only).
    • Hit-field junk. Scoping also removes other projects' text values and the ontology entities in the ontology graphs from the candidate set. In-project text values still hit and are joined away as today (DEV-6851 fixes that at the index).
    • Port boundary. Search reaches the data graph only through ProjectDataGraphs (slice/search/ports/ProjectDataGraphs.scala); never through KnoraProjectService (ARCH-MAP webapi-search rule). The GRAPH-naming SPARQL is the temporary ADR-0011 exception that ADR-0012 already names for this route.
    • Unknown project and SystemProject. Unknown → ProjectDataGraphs returns None → empty result, no query (same contract as /v2/search; SearchResponderV2LiveSpec already pins withProjectDataGraph). SystemProject resolves to its data graph, which holds no labelled resources, so it answers 0, as on /v2/search.
    • Response for an unknown project. Today the query runs and createApiResponse returns an empty ReadResourcesSequenceV2 with mayHaveMoreResults = false. The short-circuit returns the same value (the case-class defaults), so the JSON-LD ({}) does not change.
    • SPARQL rules. sparql"..." interpolator only, typed Iri/Literal holes, no string building (docs/development/dsp-api-sparql-queries.md). Imports at the top (InternalIri; drop the now unused ProjectIri import, which -Wunused:all -Werror would otherwise reject). No fully qualified names in code.
    • Test data trap. books-data.ttl is loaded into http://www.knora.org/data/0001/books, which is not project 0001's data graph (.../0001/anything). A scoped label search on 0001 therefore no longer finds books resources. No existing test combines books with limitToProject (checked: SearchEndpointsGetSearchE2ESpec searchbylabel cases and SearchResponderV2Spec label cases all pass limitToProject = None). New tests must use anything-data or incunabula-data fixtures, which are loaded into their projects' data graphs.
    • Interplay with DEV-6851. No open PR or branch touches SearchQueries.scala (checked 2026-10-23: open PRs #4399, #4398, #4395, #4390, #4365, #4361, #4196; no *6851* branch). DEV-6851 will change the text:query argument; with this plan it changes in one place (labelLookupClause).
    • Stacking. The PR is stacked on #4399 (DEV-7492), restacked at finalization. Execution happens on this branch, based on main. #4399 also edits ADR-0012, ARCH-MAP.md, docs/development/dsp-api-fuseki-query-execution.md and SearchResponderV2.scala (other methods), so the restack may need small textual conflict resolution in those files. The docs edits here are deliberately small, dated additions to keep that cheap.

    Acceptance Criteria

    • With limitToProject set to a known project, both label queries wrap only text:query in GRAPH <dataGraph> { } and emit no attachedToProject restriction (goldens).
    • Without limitToProject, both queries equal the current unscoped shape after Jena canonicalisation (legacy fixtures byte-unchanged).
    • The class restriction still walks rdfs:subClassOf*, outside the GRAPH.
    • An unknown project returns 200 with an empty page and count 0 without querying; an invalid term is still a 400.
    • IT and E2E tests show in-project hits kept, other projects' hits dropped, and scoped counts equal to the unscoped counts filtered to the project.
    • ADR-0012, Fact 10, the Search context, ARCH-MAP and the endpoint docs reflect the extension.
    • just check, bazel test //modules/webapi:test, just test-it and just test-e2e pass.

    Dependencies & Risks

    • Deployment constraint (for the PR body). Ship only in a release at or after the one that delivers the #4393/#4394 Fuseki image (Lucene text:graphField) to each environment. A scoped lookup returns 0 on an index without the graph field, so a project-restricted typeahead would silently return nothing. Never deploy with SKIP_AUTO_INDEX_REBUILD=true. Dev has the field since 2026-10-21; stage does not yet. This is the same constraint as DEV-7594 (#4396), which is already on main, so this PR adds no new rollout order.
    • Test images. IT/E2E need Fuseki test images with the graph field (just docker-load-test-images); the SearchResponderV2Spec stale-index detector fails loudly otherwise.
    • Restack conflicts with #4399 in shared docs files (see Technical Considerations), low effort.
    • One-graph rule. Without attachedToProject, a resource whose label triple sat in another project's graph would be found by the wrong project's scoped search. Stage had none on 2026-10-21; ADR-0012 already accepts this.

    Decisions taken unattended

    1. Go, not won't-do. The measured gain is 1.5–8× and up to 2 s per keystroke, with equal results, so the ticket's own won't-do condition (gain within noise) is not met.
    2. Builder takes dataGraph: Option[InternalIri] instead of limitToProject. This mirrors SearchFulltextQuery.build. It makes the unscoped+attachedToProject shape unrepresentable rather than keeping a dead branch, and the unknown-project short-circuit makes that safe.
    3. Unknown project short-circuits to empty (no query). This is the same contract as /v2/search, via the shared withProjectDataGraph. The observable response is unchanged.
    4. Legacy *WithProjectAndClass fixtures are kept and compared without the join, using the SearchFulltextQuerySpec technique, rather than deleted. They keep pinning the unscoped class-restricted shape, and the new scoped shapes get exact-text GoldenTest goldens.
    5. The E2E and IT cases use incunabula/anything fixtures, not books. books-data is loaded into a graph that is not project 0001's data graph. Moving it would touch many unrelated specs, so this plan leaves it alone. The trap is recorded in a test comment.
    6. No scoping of the class walk or other patterns. Only text:query goes inside the GRAPH (ADR-0012 Decision 2), and the subClassOf* closure is kept as is (DEV-6833, ticket scope item 2).
    7. The docs get dated notes in existing files and no new ADR. This is an extension that ADR-0012's Consequences already anticipate for this route.
    8. Measurement on dev used rendered SPARQL through dsp-cli, not the API. This isolates the query change. API-level overhead is identical in both modes.
