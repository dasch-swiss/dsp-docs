    fix: Harden the fulltext breadth guard for Gravsearch traffic

    Overview

    FulltextBreadthGuard (DEV-6864) now guards every Gravsearch matchFulltext prequery as well as /v2/search (#4399), and those prequeries run with the full 1M Lucene hit limit. DEV-7623 lists five weaknesses that matter more under Gravsearch traffic. This plan fixes items 1–3 in the guard, settles item 5 (span status of a refusal), removes the unused resourceClass from the cache key, and records the item-4 cap measurement taken on stage during planning (see Item 4: stage measurements).

    Problem Statement / Motivation

    All references are to modules/webapi/src/main/scala/org/knora/webapi/slice/search/FulltextBreadthGuard.scala unless stated otherwise.

    1. Fork before cache check. guarded forks the real query and only then awaits cache.get(key). A term whose over-cap verdict is cached still starts the broad 1M-limit prequery, sends it to Fuseki, and interrupts it. The interrupt cancels the sttp request, but Fuseki likely (unverified) keeps evaluating until it writes output or hits the timeout parameter sent with the request (120 s on the Gravsearch tier, TriplestoreServiceLive.executeSparqlQuery). Every retry of a refused term therefore costs Fuseki work.
    2. Unbounded verdict wait. The probe runs under one semaphore (max-concurrent = 8) shared by /v2/search and Gravsearch. A request whose query has already finished still waits for its verdict, up to the probe's 60 s tier timeout when the probe is queued or slow. A burst of distinct broad terms stalls fast queries.
    3. Fail-open amplification. A failed probe is cached for Duration.Zero, so under Fuseki stress every request re-probes (adding load) and then runs unguarded, now with the 1M limit instead of 10k.
    4. Cap unmeasured for Gravsearch. v2.fulltext-search.probe.cap = 250000 was tuned for /v2/search.
    5. Refusal is an ERROR span. A refusal ends gravsearch.prequery.execute (and the root gravsearch span) with ERROR "…: BadRequestException", although the HTTP SERVER span marks only 5xx as ERROR (DspApiServer.httpStatusMapper). /v2/search has no stage spans, so it is not affected.
    6. Cache key (in the ticket's description, not one of its five items). BreadthKey.resourceClass is not measured by the probe, so class-restricted /v2/search requests split cache entries for no gain (Gravsearch always passes None).

    Proposed Solution

    • Item 1 — cache-first refusal. The guard keeps a small, bounded memo of over-cap verdicts, written by the probe lookup itself whenever a probe returns a count above the cap. guarded consults the memo before forking: a known over-cap term is refused without starting the query and without probing. Only a miss or a known within-cap verdict forks the query (concurrently with the probe, as today).

    • Item 2 — bounded verdict wait. Once the query has succeeded the guard waits at most verdict-wait (new config, default 5 s) for the verdict. No verdict by then → return the query's result (fail open: the expensive work is already done, refusing it protects nothing). A query that failed before the verdict returns its failure at once: waiting could only swap one error for another (a Lucene-syntax 400 or a timeout 503 for the "too broad" 400). The probe is not interrupted; it runs in a fiber forked into the guard's own scope (not the request's), completes in the background, and its verdict lands in the cache and memo for the next request. While the query is still running, the verdict is awaited as today (an over-cap verdict still interrupts the query). The shared semaphore stays (see Decisions). Shape of guarded after Phase 3 (a sketch, not a contract; names are illustrative):

      for {
  _        <- ZIO.fail(tooBroad(searchTerms)).whenZIO(memo.isOverCap(key))      // Phase 2
  queryFib <- query.fork                                                        // request-scoped child
  probeFib <- ZIO.interruptible(cache.get(key)).forkIn(scope)                   // guard-scoped
  first    <- probeFib.await.raceEither(queryFib.await)                         // never fails
  result   <- first match {
                case Left(Exit.Success(n)) if n > cap => queryFib.interrupt *> ZIO.fail(tooBroad(searchTerms))
                case Left(_)                          => queryFib.join              // within cap or fail open
                case Right(queryExit) if queryExit.isFailure => ZIO.done(queryExit) // no verdict wait
                case Right(queryExit)                 =>
                  probeFib.await.timeout(verdictWait).flatMap {
                    case Some(Exit.Success(n)) if n > cap => ZIO.fail(tooBroad(searchTerms))
                    case _                                => ZIO.done(queryExit)
                  }
              }
} yield result

      The probe is observed with await, never join: a probe fiber that ends interrupted (scope closed) must fail open, not interrupt the request. Interrupting the loser of raceEither interrupts only an await fiber, never the probe or the query. ZIO.interruptible resets the interruptibility the fork would inherit from an uninterruptible caller (zio/zio#11044), so closing the scope cannot hang on a probe. Forking the probe into the guard's scope also fixes a latent cross-request bug: in zio-cache 0.2.4 the lookup runs in the fiber that first calls get, and interrupting that fiber interrupts the entry's promise and removes the entry, so a second request awaiting the same probe (dsp-app's page + count pair) was interrupted with it. - Item 3 — negative cache TTL. A failed probe is cached for failure-ttl (new config, default 30 s). Within that window requests fail open without re-probing, so a stressed Fuseki is not hit by a probe per request. Fail-open itself is kept. - Item 4 — cap. See Item 4: stage measurements for the data and decision. - Item 5 — span status. In Gravsearch stage spans a BadRequestException is a client rejection: status stays UNSET, gravsearch.exit_reason = bad_request is set, and the description/error.type are not written. Every other typed failure, defects and interruptions keep today's sanitized ERROR handling. Implemented as an optional classifier parameter on SanitizedSpan.withSpan (default: none, so the SPARQL passthrough span is unchanged) that SearchResponderV2.stageSpan supplies. - Cache key. BreadthKey drops resourceClass; guarded drops its limitToResourceClass parameter. The probe SPARQL is the key, so if the probe ever measures the class restriction, the key changes with it.

    Item 4: stage measurements

    Measured on stage on 2026-10-23 with dsp vre sparql query -s stage (never a local dump). The raw data was not kept.

    • Shapes. The Gravsearch count prequery as the golden GravsearchToCountPrequeryTransformerE2ESpec__classlessMatchFulltext.txt renders it (unscoped, 1M hit limit; FILTER NOT EXISTS blocks reformatted onto one line):
      • class-restricted: VALUES holds one class, ekws:Object (0812, the class with most ver* hits after a 0105 class; it has no subclasses);
      • classless (knora-api:Resource): VALUES holds all 936 resource classes on stage, as the generator emits for a classless query.
    • Scoping. Stage lacks the Lucene graph field (#4393/#4394): a GRAPH-scoped lookup returned the repository-wide hit count (63,564 for ver* in the 0812 graph). Only unscoped shapes were measured.
    • Candidates are the probe's COUNT(DISTINCT ?m). Probe time for every term was 0.3–3.4 s.

    Count prequery, median of 3 sequential runs (first run, typically 2–3× slower and cold, in brackets); > 120 s is the store's 120 s timeout, i.e. the Gravsearch tier would also have failed:

    shape term probed candidates resources time (first run)
    class-restricted Bild* yes 47,421 37,553 5.4 s (15.8 s)
    class-restricted ver* yes 63,368 7,883 8.0 s (21.4 s)
    class-restricted der no 132,516 48,141 15.7 s (33.4 s)
    class-restricted Basel* yes 153,441 2,388 15.8 s (28.7 s)
    class-restricted un* yes 248,461 18,523 73.3 s (94.6 s)
    class-restricted in de yes 348,567 — > 120 s (all 3 runs)
    classless Zeitglöcklein no 4 2 1.0 s (1 run)
    classless Zeichnung* yes 1,210 1,054 72.8 s (73.2 s)
    classless Papier* yes 2,857 — > 120 s (1 run)
    classless Brief* yes 13,577 — > 120 s (1 run)

    Findings:

    • Class-restricted: at the cap (un*, 248k) the count stays under the 120 s Gravsearch tier (73 s, about 60 %); just over it (in de, 349k) every run times out. Cost is not linear in candidates (153k: 16 s, 248k: 73 s), so the cap sits close to the tier's edge, but on the right side of it. dsp-app sends page and count together, so the load at the cap is roughly doubled.
    • Single plain word (never probed): der (132k) costs 16 s. No single word on stage reached the cap (the broadest found: in, 180k), so the shouldProbe rule is not a gap for this shape.
    • Classless: the cost is the outer VALUES join over all 936 resource classes, about 70 ms per matched resource. The same query without that join returns the same 1,054 resources in 0.79 s (control run). A classless matchFulltext exceeds the tier from about 2–3k candidates, three orders of magnitude below the cap. No breadth cap can fix this without refusing almost every term. This contradicts the 2026-10-08 Lucene-hit-limit measurements (classless the: 72,900 resources in 32 s), whose prequeries may not have carried the full-class VALUES; it needs confirming against a prequery captured from a real request (H1).

    Technical Considerations

    • zio-cache 0.2.4 has no non-blocking getIfPresent; contains/entryStats also see pending or expired entries, so a pre-fork check built on them would block on an in-flight probe or re-probe serially. Hence the guard-owned memo. It is a Ref of key → expiry instant, bounded by cache-capacity (drop expired entries first, then the oldest), expiry cache-ttl, read with Clock so TestClock drives it. Expiry uses the same strict isAfter rule as zio-cache's hasExpired (verified in the 0.2.4 source by review).
    • Memo write ordering. The memo is written inside the cache lookup, after the probe returns and before the lookup completes the cache entry. So any caller that has seen an over-cap verdict (from the cache or the in-flight promise) is guaranteed to find it in the memo afterwards; tests rely on this for determinism. Because the memo is stamped a moment before zio-cache stamps its entry, and the two evict by capacity independently, a term can briefly miss the memo while the cache still holds its over-cap verdict: its query is forked and interrupted at once, as today. Accepted; not worth coupling the two stores.
    • Background probe. In zio-cache 0.2.4 the lookup runs in the fiber that first calls get; interrupting that fiber abandons the lookup and interrupts every other waiter on it. The probe therefore runs in a fiber forked with ZIO.interruptible(cache.get(key)).forkIn(scope) into a scope the guard captures in make (the layer's ZLayer.scoped scope in production, the test's scope in specs), still bounded by the semaphore. Not forkDaemon: a daemon outlives application shutdown and test teardown (a gated test probe would leak forever). make becomes URIO[Scope, FulltextBreadthGuard]; the specs that call it gain Scope (Spec[TestEnvironment & Scope, Any] or ZIO.scoped). Review checked the lookup semantics against the zio-cache 0.2.4 source (from a fetched summary, not verbatim); the executor re-confirms them before relying on them, and the "probe completes in the background" and "a second waiter is not interrupted" tests are the guard.
    • Backlog (accepted risk). A background probe keeps its place in the semaphore queue after its request is gone, so a burst of distinct broad terms leaves up to one queued probe per distinct key (single-flight), each bounded by the 60 s search-timeout tier once it holds a permit. Today the same probes run while their requests wait, so total probe work is unchanged; only work for abandoned requests is new. Under such a burst a probe can take longer than verdict-wait to reach a permit, so requests fail open exactly while the queue is long; the verdict still lands for the next request. No extra bound is added and no timeout is put around cache.get (interrupting a lookup would bring back the waiter-interrupt bug); revisit if the SearchProbe tier metrics show a growing queue. The DEV-6864 plan intended "skip probing rather than queue on contention"; the shipped guard queues, and this plan keeps that (skipping would let a burst bypass the guard entirely).
    • Page and count pairs (accepted). dsp-app sends page and count together. Both miss the memo and start their 1M-limit prequery while sharing one probe; when the page fails open after verdict-wait, the count can already be refused from the memo, so the UI may show results and then a count 400. Pre-existing in the first half (both queries always started); the second half is the price of the bounded wait, and the next request for the term is consistent.
    • Interrupted lookups are not cached. zio-cache 0.2.4 stores no entry for an interrupt-only lookup exit (it interrupts the promise and removes the key), so failure-ttl never applies to a probe cut short by scope close; a probe timeout is a failure and is cached for failure-ttl (fail open, Decision 4).
    • Trace shape. The probe fiber inherits the request's trace context at fork time, so its CLIENT span stays under gravsearch.prequery.execute but may now end after that span (and the root) when the verdict wait expires. OpenTelemetry allows this; the runbook says so (Phase 3).
    • Interruptibility. The query fork and its interrupt inherit the caller's interruptibility (zio/zio#11044 pattern, journal of DEV-7492). Production handlers are interruptible; unchanged here. The probe fork resets it explicitly (ZIO.interruptible), because it lives in the guard's scope and must be interruptible when that scope closes, whatever the caller was.
    • Observability recipe. SanitizedSpan.unsetOnFailure stays UNSET (load-bearing). The new branch only skips markSanitizedError for a classified client rejection; it never writes a description, so it cannot leak. The classifier sees only a pure typed failure: it is consulted only when cause.failureOption is defined and the cause holds no defect and no interruption, so the defect-carrying and interruption branches are untouched. docs/observability/instrumentation-recipe.md §7 gains the client-rejection bullet.
    • /v2/search and item 5. /v2/search opens no SanitizedSpan; its refusal surfaces only on the HTTP SERVER span, which DspApiServer.httpStatusMapper already leaves non-ERROR for a 400. So after Phase 5 a breadth refusal is non-ERROR on every span the API owns, on both endpoints. The sttp CLIENT span of a prequery that a refusal interrupts is the library's, identical on both endpoints and out of scope; Phase 2 removes it for every repeat refusal, because the query is no longer started.
    • Dashboard. grafana-dashboards/dsp-api/dsp-gravsearch.json reads the root span's status from span metrics: the panels "Error / interrupt share (range)" and "Query rate by outcome" describe STATUS_CODE_UNSET as success. After Phase 5 a 400 rejection is UNSET too, so the two panel descriptions must say so (description text only; queries unchanged).
    • Config. New keys under app.v2.fulltext-search.probe: verdict-wait, failure-ttl, both added to FulltextSearchProbe, validated in AppConfig (positive; failure-ttl <= cache-ttl), and asserted in AppConfigSpec.

    Decisions taken unattended

    Planning ran unattended; these were decided by the planner acting for the owner, with reasons.

    1. Item 1: memo, not probe-first. Probing before every query would tax admitted terms (DEV-6864 Spike A chose concurrency for that reason). Checking only known verdicts first removes the repeat cost at no tax.
    2. Item 1 test: the Fuseki-thread IT is not feasible. To the planner's knowledge (not verified against the test container) Fuseki exposes no running-query introspection (/$/stats and /$/metrics count requests, not active executions), and whether ARQ stops on a client disconnect would only show when it next writes output, so an IT would be timing-dependent and flaky. Replacement: unit tests proving a known over-cap term never starts the query effect (no HTTP request is made, so no Fuseki thread is used), plus the existing test that an in-flight query is interrupted. The remaining exposure (the first refusal per term per cache-ttl) is bounded by the 120 s timeout parameter Fuseki receives with every Gravsearch query.
    3. Item 2: bounded wait, shared semaphore kept. A separate Gravsearch semaphore would raise the ceiling of concurrent probes on Fuseki and would not fix a slow probe; a bounded wait fixes both causes of the stall. 5 s covers every measured probe (≤ 3.4 s at 349k candidates) with headroom. A failed query returns at once without waiting: the verdict could only replace one client error with another. The background-probe backlog and the page/count inconsistency are accepted (Technical Considerations).
    4. Item 3: negative TTL, fail-open kept, no circuit breaker. Failing closed under stress would refuse every probed term exactly when users retry most; the negative TTL removes the probe amplification, and each unguarded query stays bounded by Fuseki's server-side timeout.
    5. Item 5: client rejection is not ERROR. The HTTP SERVER span already treats 4xx as non-error; for the breadth refusal and the other BadRequestException rejections, stage spans now agree (a parse failure, also a 400, deliberately stays ERROR, see below). Scoped to BadRequestException (always a 400 in Gravsearch: breadth refusal, invalid Lucene syntax, generator input checks). GravsearchException stays ERROR, because it also signals server-side invariant failures (e.g. the count-row check in fulltextSearchCount), so parse failures keep their runbook topology.
    6. Cache key without resourceClass. The key is the probe SPARQL; it stays correct by construction.
    7. Item 4: keep one cap of 250,000; no Gravsearch-specific cap. The class-restricted shape at the cap stays inside the 120 s Gravsearch tier and fails just above it, so the cap does its job there; a lower Gravsearch cap has no measured point to sit on (nothing between 153k/16 s and 248k/73 s). The classless shape cannot be protected by any cap a user could live with (~2k), so its cost is a prequery-generation problem, filed as a follow-up (H1), not a guard setting. Single plain words stay unprobed.
    8. Instruction conflict. DEV-7492's decided behaviour 2 says Gravsearch uses "the same cap, same cache, same concurrent probe, same fail-open" as /v2/search. DEV-7623 explicitly reopens the cap, fail-open and probe behaviour; per the conflict rule the ticket wins. The fixes still apply to both callers identically. The same applies to DEV-6864's choices of Duration.Zero for a failed probe (replaced by failure-ttl) and of forkDaemon for the probe (replaced by forkIn on the guard's scope, so the probe still finishes and populates the cache unless the application is shutting down).
    9. No execution journal is created. The planning skill forbids plans owning or referencing the journal; the execution skill creates it.

    decided_behaviours

    Later reviewers must not undo these without a new owner decision.

    1. A term with a known over-cap verdict is refused before its query is started or probed.
    2. Once the query has succeeded, the guard waits at most verdict-wait for the verdict, then returns the query's result; a query that failed first returns its failure without waiting. The wait's timeout does not interrupt the probe, which runs in the guard's scope and caches its verdict.
    3. While the query is still running, an over-cap verdict interrupts it and refuses with a 400 (unchanged).
    4. One probe semaphore is shared by /v2/search and Gravsearch.
    5. A failed probe is cached for failure-ttl; the guard fails open (never refuses on a probe error).
    6. BreadthKey is the probe SPARQL only; guarded takes no resource class.
    7. In Gravsearch stage spans a BadRequestException leaves status UNSET and sets gravsearch.exit_reason = bad_request; every other failure keeps the sanitized ERROR status. SanitizedSpan.unsetOnFailure stays UNSET.
    8. One probe.cap (250,000) serves /v2/search and Gravsearch; FulltextSearchTerms.shouldProbe is unchanged.

    Implementation Phases

    Test commands (verified against modules/webapi/BUILD.bazel and modules/test-it/BUILD.bazel). --test_filter is a Java regex matched against the full test name, so it is always wrapped in .*….* (docs/development/dsp-api-conventions.md). GravsearchFulltextBreadthGuardSpec is an E2EZSpec and needs Docker and the test images (just docker-load-test-images); on a local Colima setup add --test_env=DOCKER_HOST --test_env=TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock to every //modules/test-it command. SanitizedSpanSpec and SearchResponderV2StageSpanSpec use in-memory tracing and need no containers. The //modules/test-it targets are tagged exclusive and bind one port, so run them one after another, never in parallel. Unattended executors must not read through bazel-* symlinks or the plugin cache (permission prompts stall the run).

    TestClock rules for every new guard test:

    • zio-cache and the memo read the Clock captured at make, which in ZIO Test is the TestClock, so make must run inside the test.
    • An entry is expired only when now is strictly after its expiry (zio-cache hasExpired, mirrored by the memo). Advance past a TTL by the TTL plus one millisecond. A TTL of Duration.Zero under a frozen clock never expires, so a "within the TTL" assertion must advance the clock inside the window first, or it passes vacuously.
    • Before advancing past verdict-wait, wait until the guard's timeout is registered: TestClock.sleeps.flatMap(s => ZIO.yieldNow.as(s)).repeatUntil(_.nonEmpty). The timeout registers only after the query finishes; adjusting earlier makes the test hang.

    Phase 1: Drop resourceClass from the breadth cache key

    Chunks: 1.

    • BreadthKey holds only probeSparql; its scaladoc states the key is the probe SPARQL and why that stays correct
    • guarded drops limitToResourceClass; the two /v2/search call sites and executePrequery in SearchResponderV2.scala are updated
    • FulltextBreadthGuardSpec and GravsearchFulltextBreadthGuardSpec call sites updated
    • New responder-level test in GravsearchFulltextBreadthGuardSpec (a guard-level test is vacuous once guarded takes no class): two fulltextSearchCountV2 calls for the same wildcard term, differing only in limitToResourceClass, run one probe (counting probe double)
    • Canary: temporarily give each call a distinct cache key (e.g. append the class IRI to probeSparql in the responder); the new test fails; revert
    • Run bazel test //modules/webapi:test --test_filter='.*FulltextBreadthGuardSpec.*'; it passes
    • Run bazel test //modules/test-it:test --test_filter='.*GravsearchFulltextBreadthGuardSpec.*'; it passes
    • Phase review: adversarial review of this phase's commits; verified findings fixed before the next phase starts

    Phase 2: Refuse a known over-cap term before starting its query (item 1)

    Chunks: 1.

    The lookup still runs in the request fiber in this phase, so the cross-request interrupt bug (Proposed Solution, item 2) persists until Phase 3.

    • Over-cap memo in FulltextBreadthGuard.make: a Ref of key → expiry instant, bounded by cacheCapacity (drop expired entries, then the oldest), expiry cacheTtl with strict isAfter semantics, read with Clock; written inside the cache lookup when the count exceeds the cap, before the lookup completes (see Technical Considerations)
    • guarded checks the memo before forking; a hit fails with the existing tooBroad 400 without running the query or the probe
