    fix: restrictions overview counts user link values, with count queries classified in Scala

    Overview

    The fix has two parts:

    1. Include user link values in every count and every drill-down. Exclude only standoff link values (knora-base:hasStandoffLinkToValue).
    2. Use the fastest measured query shapes, from the stage measurement in 01-…-design.md:
    3. Step 1 uses R. Step 2 uses C5 for each class, in batches of resources so that each query stays under the timeout.
    4. The by-property counts come from the C5 rows of all classes, in a cache for each project.
    5. Scala does all classification.

    The drill-down keeps its paging in SPARQL. Its REGEX prefilter changes to an exact list of restricted permission literals, and Scala makes that list.

    Problem Statement / Motivation

    The report has three problems:

    • Link values. Every value query has FILTER NOT EXISTS { ?value a knora-base:LinkValue . } (13 sites in ViewRestrictionsRepo and ViewRestrictionsByPropertyRepo). isValueProperty also rejects isLinkValueProp. As a result, restricted user links are not visible: 428,682 values on LIMC and 42,635 on BEOL. The report is a migration-readiness gate.
    • REGEX. The drill-down REGEX does not agree with PermissionUtilADM for some literals, for example V knora-admin:UnknownUser|RV knora-admin:KnownUser. It drops rows that are restricted for authenticated users.
    • Speed. Step 1 takes 2.5–16.4 s. R takes 0.4–2.8 s and gives identical counts. The by-property loop sends one query for each property and takes 23–156 s for each project.

    Proposed Solution

    Endpoint Today After
    /classes class discovery + 2 multi-type probes + resource counts R, classes filtered in Scala
    /values valueCountsByPermissionQuery (2 templates) C5 for the class in resource batches, from the cache, folded in Scala for each item type
    /properties ontology cache unchanged; the filter now accepts user link value properties
    /property-values valueCountsQuery for each property C5 rows of all classes, from the cache, filtered to the property in Scala
    /items, /property-items REGEX + LinkValue filter FILTER (?permissions IN (…)) with Scala-classified literals; standoff excluded by ?prop; class bound directly

    R and C5 are copied exactly from the design doc. Their pattern order is load-bearing. A ?value pattern with two bound terms makes Jena scan the whole store.

    # R
SELECT ?resClass ?permissions (COUNT(*) AS ?cnt)
WHERE {
  ?resource knora-base:attachedToProject $project .
  ?resource a ?resClass ;
    knora-base:hasPermissions ?permissions ;
    knora-base:isDeleted false .
}
GROUP BY ?resClass ?permissions

# C5
SELECT ?prop ?permissions ?valueDeleted (COUNT(*) AS ?cnt) (COUNT(?comment) AS ?commented)
WHERE {
  ?resource a $resourceClass .
  ?resource knora-base:attachedToProject $project .
  ?resource knora-base:isDeleted false .
  ?resource ?prop ?value .
  ?value knora-base:hasPermissions ?permissions .
  ?value knora-base:isDeleted ?valueDeleted .
  OPTIONAL { ?value knora-base:valueHasComment ?comment . }
}
GROUP BY ?prop ?permissions ?valueDeleted

    Decisions

    These decisions are fixed for this plan:

    1. By-property counts. They come from the cached C5 rows, as the design doc recommends.
    2. Multi-typed resources. They count once for each type. ProjectClasses, anyMultiTypedResourceQuery and multiTypedQuery are removed. The current code keeps a most-specific-class filter, so that a resource with a class and its subclass counts once (Scaladoc of ProjectClasses.resClassPatterns). That filter needs a subClassOf+ probe of up to 27.3 s on LHTT, and R and C5 have no resource IRI to remove duplicates with. None of the three measured projects has a multi-typed resource, so the filter costs time and changes no count.
    3. REGEX. The REGEX is replaced in this plan.
    4. Link item type. A link value counts as item type Value. There is no new Link item type, so the API and dsp-app do not change.
    5. Structural links. isPartOf, isRegionOf, isAnnotationOf and hasRepresentation count as user links. Only standoff links are excluded.
    6. Batched value counts. The value counts of a class are read in batches of resources, so each query stays under the 40 s timeout as projects grow. Paging the grouped result rows with LIMIT/OFFSET would not bound the query time, because each page must scan and aggregate the whole class. The project-wide resource counts stay one query.

    Technical Considerations

    Classification

    The classification is a set of pure functions and stateless data. No class holds state.

    • Location. The types and pure functions go in the slice domain (slice/admin/domain/service/):
      • ValueKind with ValueKind.of(info: ReadPropertyInfoV2): Option[ValueKind].
      • ProjectOntologyIndex with the pure builder ProjectOntologyIndex.from(properties, classes).
      • object ValueCountFold with the fold functions.

    The repo does SPARQL and row parsing only. ValueCountRow is a repo output, so it goes in the ViewRestrictionsRepo companion, next to PermissionCountRow. - Shared visibility. classify and foldRows are duplicated today (ViewRestrictionsService.scala:71,94, ViewRestrictionsByPropertyService.scala:96,115). Move them into ValueCountFold, and let both services use the one copy.

    enum ValueKind { case Plain, File, Link }

final case class ProjectOntologyIndex(
  resourceClasses: Set[String],
  valueProperties: Map[String, ValueKind], // hasStandoffLinkToValue is absent
)

// ViewRestrictionsRepo companion
final case class ValueCountRow(
  classIri: String,
  propertyIri: String,
  permissions: String,
  deleted: Boolean,
  count: Int,
  commented: Int,
)
    • Index. ProjectOntologyIndex comes from OntologyRepo.findAll (all cached ontologies, knora-base and shared ontologies included). Only that call is an effect, and it runs in the service. Property and class IRIs are unique across all ontologies, so one index for every ontology is correct. With it, values of a property from a shared or other-project ontology still count, as they do today through subPropertyOf*. /properties keeps its list from the project ontologies plus knora-base.
    • Class list. /classes lists the resource classes that have one or more non-deleted resources (from R). A class whose resources are all deleted is no longer listed. Today it is listed with population 0.
    • totalValues. The total for each item type is the sum of the rows of that type: All gives the value count, File the File rows, Value the Plain and Link rows, and Comment the sum of commented.
    • Folding. The folding uses the index:
      • It drops deleted rows.
      • It drops properties that are not in the index: link targets, metadata and standoff links.
      • It maps each row to item types: All gives count, File gives File rows, Value gives Plain and Link rows, and Comment gives commented.
      • It reports unknown property IRIs with one ZIO.logWarning line for each fold, not one line for each row.
      • It is total: no .get, no unsafeFrom.

    Cache

    The cache uses zio.cache.Cache 0.2.4. Concurrent get calls for one missing key share one lookup (single-flight). This matters because the app sends /property-values requests in parallel.

    • Structure. A new final case class ViewRestrictionsRowCache holds two caches, with a ZLayer.scoped layer. It follows AssetPermissionsCache.scala:34-36,76-82,99-110: a testable makeCache(capacity, ttl)(resolve) built with Cache.makeWith, and a CacheKey case class in the companion. The loaders come from the repo. The repo layer then needs only TriplestoreService, and the EhCache viewRestrictionsProjectClasses and its CacheManager wiring go away. Both services take ViewRestrictionsRowCache as a constructor argument.
    • Keys. One cache holds the R rows for a project (key ProjectIri). One cache holds the C5 rows for a class (key C5Key(projectIri: ProjectIri, classIri: String)).
    • Settings. TTL 10 minutes and capacity are companion vals, as ProjectClassesTtl is today. A failed lookup is kept for Duration.Zero, so a timeout does not block a key for 10 minutes.
    • Removal. zio-cache 0.2.4 has no way to list keys (only invalidate(key) and invalidateAll). On /classes, the service reads the current R rows of the project and calls invalidate for each C5Key of those classes. Then it calls invalidate for the R key and loads R again. An entry for a class that is gone from R stays until its TTL ends. A load that runs at the same time can insert an entry again after the removal. The TTL limits this.
    • Lifetime. Only /classes removes the entries of its project, because it starts a class-report run. /properties does not remove entries, so a change from the class tab to the property tab reuses the rows. A reviewer sees a permission change at the next class-report page load, or after 10 minutes at most.
    • Drill-down from a new cache. /property-items needs the literals of the property, so on a new cache it also loads all classes first. The app normally opens the drill-down after the counts are loaded, so the cache is usually ready. A deep link on a new cache waits for the same load as /property-values.
    • Multi-typed resources, by property. A multi-typed resource counts once for each type, also in /property-values. The property drill-down keeps DISTINCT values. For such a resource, the property total and the drill-down can therefore differ. This follows from decision 2, and the Scaladoc documents it.
    • By-property load. On a new cache, /property-values loads every class with ZIO.foreachPar(classes)(…).withParallelism(4). On LIMC, the slowest class takes 22 s and all classes take 64 s in sequence. The wall time is therefore about 22–25 s, below the 40 s query timeout. This number is not measured yet; Phase 6 measures it.

    Batched value counts

    The value counts of one class come from two steps:

    1. List. One query lists the IRIs of the class's live resources: ?resource a $resourceClass ; knora-base:attachedToProject $project ; knora-base:isDeleted false. It has no value join and no aggregate.
    2. Count. The value-count query runs once for each batch of ValueCountBatchSize resource IRIs, with VALUES ?resource { … } as the first pattern, so ?resource is bound before ?resource ?prop ?value. The other patterns and the pattern-order rule stay as they are.

    Scala sums the batch rows by (property, permissions, deleted). The batches are disjoint, because a value belongs to one resource, so the sum equals the unbatched result. The cache keeps one row set for each class; only its loader changes. Batches of one class run with a parallelism limit, so one class does not take all triplestore capacity.

    Limits that stay:

    • Listing. The listing query still grows with the class size. It reads one index and returns only IRIs. If the measurement shows that it does not stay well under the timeout for the largest measured class, it needs its own paging (follow-up).
    • Total time. The total time for each class still grows linearly with its size. The 40 s timeout applies to each query, not to each request.
    • Batch size. ValueCountBatchSize is a measured constant, not a guess. The measurement in Phase 3 sets it so that the slowest batch query on LIMC stays under 10 s, which leaves room for growth.

    Drill-down

    The drill-down keeps its current shape and its paging in SPARQL. It changes in four places:

    • Standoff links. FILTER NOT EXISTS { ?value a knora-base:LinkValue . } changes to FILTER (?prop != knora-base:hasStandoffLinkToValue) in the class repo. This compares a bound variable and needs no index lookup. Jena does not rewrite != by default (TransformFilterInequality is off). In the property repo, the filter goes away, because the property is bound.
    • REGEX. FILTER (!REGEX(?permissions, …)) changes to FILTER (STR(?permissions) IN (…)). The list holds the literals that are restricted for one or more audiences:
      • The resource branch uses the restricted literals of the R rows of the class.
      • The value branch uses the restricted literals of the C5 rows of the class.
      • The property drill-down uses the restricted literals of the C5 rows for the property.

    The All page and count queries thus carry two lists, one for each UNION branch. The drill-down and the counts agree by construction. - Why STR(). Jena 6.2.0 rewrites ?permissions IN ("a", "b") with plain string literals by default: TransformExpandOneOf makes a disjunction, and TransformFilterDisjunction with TransformFilterEquality makes a UNION with the literal in the triple pattern. Then ?value knora-base:hasPermissions "a" has two bound terms and scans the whole store. STR(?permissions) is not a variable, so the equality transform does not apply. A unit test runs Algebra.optimize(Algebra.compile(query)) on each rendered drill-down query. It asserts that the optimized algebra has no knora-base:hasPermissions triple with a constant object. The test proves only that the filter is not rewritten. It cannot show the final BGP order of TDB2. - Literals. The literals go into the query through Literal.string, which escapes \, " and ' (modules/sparql-builder/src/main/scala/org/knora/sparqlbuilder/types.scala:122,151-159). - Empty list. If a list is empty, its branch has no rows. If all lists are empty, the result is an empty page with a total of 0, and no query runs. - Class binding. ${classes.valuesClause}, resClassPatterns and FILTER (?resClass = $groupClass) change to ?resource a $groupClass plus BIND($groupClass AS ?resClass). The row parsers read ?resClass (ViewRestrictionsRepo.scala:195,225), so the variable must stay bound.

    Golden tests

    ViewRestrictionsQuerySpec does not use GoldenTest today. It compares the queries with ViewRestrictionsLegacyFixtures only. The files ViewRestrictionsQuerySpec__*.txt in modules/webapi/src/test/resources/org/knora/webapi/slice/admin/repo/ are not read by any spec. The plan removes those orphan files, and adds GoldenTest.assertGolden tests for R, C5 and each drill-down query (pattern: ValueHasXmlBackfillQuerySpec.scala). New golden content is captured through TEST_UNDECLARED_OUTPUTS_DIR, because rewrite = true cannot write files under Bazel.

    Test seams

    • Pure tests. ValueKind, the index builder and the fold need no layers.
    • Cache tests. They use makeCache with a counting Ref and no triplestore, as AssetPermissionsCacheSpec.scala does.
    • Service tests. They use ViewRestrictionsServiceSpec and ViewRestrictionsByPropertyServiceSpec with OntologyCacheFake plus OntologyRepoLive (pattern: CardinalityServiceLiveSpec.scala:173-182). The fixture ontology data includes the knora-base properties that the test uses.
    • Log tests. They assert log lines with ZTestLogger.logOutput (pattern: ValueHasXmlBackfillServiceSpec.scala:94).

    Unchanged

    /properties, the endpoints, the DTOs and dsp-app stay as they are.
