    feat: a service identity that is not a user, for machine-to-machine project exports

    Overview

    dsp-api gets a service identity: a caller that is not a User, authenticates with a short-lived Ed25519-signed JWT that it mints itself, and may only run the v3 project export flow (trigger, status, download, delete) for the exports it created. Trusted public keys are configured per server; with none configured the feature is off. Every service call is logged.

    The decisions below were settled with the owner on 2026-11-19 and are recorded in DEV-7936 ("Decisions"). They are not reopened here.

    Problem Statement / Motivation

    dsp-repository's Deposit Area synchronises whitelisted projects from the VRE every night: it exports the project's full data (non-public data and permissions included) from whichever dsp-api server (prod, stage, test servers) holds the project. Today every route that returns a project's full data needs a SystemAdmin user's JWT, and no machine credential exists. The pipeline's first usable increment depends on this; no interim SystemAdmin account is planned.

    dsp-api tokens are HS256 with one secret per server (JwtService.scala:74-76, modules/jwt is HS256 only). Handing that secret to a client would let it mint SystemAdmin tokens, so the service needs its own, asymmetric credential.

    Proposed Solution

    Settled decisions (DEV-7936)

    1. Ed25519 (alg: EdDSA, RFC 8037). The client holds the private key and mints its own tokens; dsp-api holds public keys only.
    2. Off by default: application.conf trusts no key; ops-deploy sets keys per server through an environment variable.
    3. A config list of trusted keys {name, kid, public key}. The name is the service identity. A token needs a listed kid, aud equal to this server's external base URL, a lifetime exp - iat of at most 15 minutes, Bearer only.
    4. Permitted: trigger an export, its status, its download, its deletion; status, download and delete only for exports the service created. Every other endpoint rejects the token (401). New Policy case. createdBy becomes user-or-service; task files written by the previous version still load.
    5. No server-side project allowlist.
    6. Export format unchanged (password hashes are in exports by design). ADR records the exposure of a leaked key.
    7. One INFO log line per call (service name, kid, jti, action, project IRI, export id) plus span attributes. jti logged, not checked for replay.
    8. dsp-api only, one PR. ADR-0014, Identity & Access CONTEXT.md, endpoint descriptions. Tests use a key pair generated in the test. The PR body documents ops-deploy settings and the token contract for the client.

    Decisions taken during planning (reversible; listed for the owner's veto)

    • P1. Key format in config. One env var KNORA_WEBAPI_SERVICE_IDENTITY_TRUSTED_KEYS holding a JSON array [{"name": "dsp-repository", "kid": "dsp-repository-2026-11", "publicKey": "<SPKI>"}], where publicKey is the base64 of the X.509 SubjectPublicKeyInfo DER, with or without PEM armour and line breaks (what openssl pkey -pubout prints). There is no list-from-env pattern in the repo (HOCON ${?VAR} yields a string); the closest precedent is the comma-separated fair.dpe-oai-shortcodes. A JSON string carries the three fields per key. A malformed array, an unparsable or non-Ed25519 key, a duplicate kid, or a blank name fails startup. An empty or whitespace-only value means "no keys", like [], because an unset-but-declared env var renders as "". Several keys may share one name (rotation overlap); kids are unique. At startup one INFO line states the number of trusted keys with their names and kids, never key material. Options weighed: comma-separated name:kid:key triples (fragile with base64), indexed CONFIG_FORCE_ env vars (unused here).
    • P2. Audience comparison. aud must match the server's external base URL after normalisation: lower-case scheme and host, default port dropped (443 for https, 80 for http), trailing slash dropped. Reason: ops-deploy sets DSP_API_PROTOCOL=https, DSP_API_PORT=443, so KnoraApi.externalKnoraApiBaseUrl renders https://api.dasch.swiss:443, while a client naturally uses https://api.dasch.swiss. aud may be a string or an array (RFC 7519 §4.1.3); one element must match. Both sides go through the same normaliser; it parses the authority by hand rather than with URI.getHost, which is null for host names containing _ (Docker service names).
    • P3. Issuer and subject. iss and sub must both equal the matched key's name. Binding the identity to the key means a token signed with one key cannot claim another service's name.
    • P4. Time checks. exp, iat and jti are required. Clock leeway 30 s: reject when now >= exp + 30s or iat > now + 30s, and when exp - iat > 15 min (no leeway on the lifetime). JwtClaim has no nbf field (unknown claims land in content), so nbf is not checked; the lifetime cap bounds the token anyway. The current time comes from ZIO Clock, so tests drive it with TestClock. The client contract recommends exp 5 minutes after iat.
    • P5. Token routing. The new factory peeks at the unverified JWS header. When alg == "EdDSA" the token goes to the service verifier and never reaches Authenticator.authenticate, which would read sub as a user IRI. Otherwise the existing user path runs and the user must be a SystemAdmin. No other endpoint base changes: the HS256 decoder rejects an EdDSA token (the signature check fails), so the token gets 401 there. A test pins that. alg is compared exactly (EdDSA); a malformed header, a missing alg or another spelling takes the user path and gets its 401. A token with alg HS256 and a service kid never reaches the service verifier.
    • P6. Not someone else's export → 404. A service asking for the status, download or deletion of an export it did not create gets 404 export_not_found, the same answer as for an unknown id, so it learns nothing about other exports. The ownership check runs right after the lookup by id and before any state check, so a service never sees 409 export_in_progress or export_failed for someone else's export, and a deletion never starts. Lookup and deletion are separate calls on the single slot; a swap of the slot between them is possible but harmless (the deletion acts on the id, which then no longer exists). SystemAdmins keep full access to every export, including the service's. Ownership is keyed on the service name, never on kid or jti, so an export created under an old key stays the service's after rotation.
    • P11. Occupied slot (revised by the owner on 2026-11-19). The slot is server-wide. When a service triggers an export while the slot holds any export, its own or anyone else's, it gets 409 export_exists with that export's id and project, exactly as a SystemAdmin does. With its own export it recovers after a crash (check status, delete, trigger again). The client contract says: on export_exists for an export that is not its own (its status answers 404), give up for this run and retry on the next one, never loop. The ticket keeps the slot collision itself out of scope; this only fixes what the service is told. Revision note: the first version answered another caller's export with a new 409 export_slot_occupied (fixed message, no id or project). The owner dropped it: exporting is a SystemAdmin or trusted-service operation, so revealing another caller's export id and project to a service is not a leak worth a separate code.
    • P7. How a service creator is written. createdBy becomes a TaskCreator with two cases, user IRI or service name, serialised as one string in both the task file and DataTaskStatusResponse.createdBy: the user IRI as today, or the IRI urn:dsp:service:<name> for a service. Old task files decode unchanged and the API field stays a string. The codec is hand-written (a derived one would emit an object): it tries the urn:dsp:service: prefix first, then UserIri.from; a string that fits neither, or a prefix with an invalid name, fails to decode. The tapir schema is an explicit Schema.string with the description "IRI of the user or service that created the task." (only the description changes in the OpenAPI output; dsp-app's generated model already types the field as a string and nothing in dsp-app or dsp-tools reads it). The enum cases are ByUser and ByService, so they do not shadow the User class. Options weighed: a JSON object for services (breaks the response's string type and the OpenAPI client), a second optional field (leaves createdBy meaningless for service tasks). Rollback: a binary from before this change cannot decode a service task file and drops it silently (readTaskJson logs and treats the file as corrupt), leaving the export directory to be cleaned by hand. The ADR and the PR body say so.
    • P8. Span attributes are bounded. docs/observability/instrumentation-recipe.md forbids traffic-bounded values (instance IRIs, ids) as span attributes, because spanmetrics can turn them into labels. The span gets the bounded ones: dsp.service.name, dsp.service.kid, dsp.service.action, and the project shortcode. jti, project IRI and export id go into the log line only. This narrows decision 7 to fit a repo rule.
    • P9. Rejected service tokens are logged too. A token routed to the service path that fails verification logs one WARN line with a fixed reason category (unknown_kid (also for a missing kid), bad_signature, bad_audience, expired, lifetime_too_long, bad_claims, disabled) and the kid only when it is a configured one. With no keys configured every service token is disabled, checked before the kid lookup. The client always gets the same fixed-text 401. The raw token is never logged. No rate limiting in dsp-api; that stays with the reverse proxy.
    • P12. Audit outcomes. The audit line carries an outcome (ok, not_owner, not_found, conflict, error), so operators can tell an ownership refusal from an unknown id although the client gets the same 404. For a download the line records that the response stream started; a download cut off mid-stream is still logged as ok. The ADR states that limit.
    • P10. Names. Policy case SystemAdminOrExportService; requirement sentence "Requires SystemAdmin permissions, or a trusted export service, which only sees the exports it created." Config section app.service-identity. Code in slice/security/ (ServiceIdentityConfig, ServicePrincipal, ServiceTokenVerifier), EdDSA mechanics in modules/jwt. ServiceName is a shared value type in slice/common/domain (next to LanguageCode), so the export domain can use it without depending on slice/security. ExportCaller lives in slice/security; the mapping ExportCaller -> TaskCreator lives in V3ProjectsRestService, the only place that needs both.

    Shape

    Bearer token ──► BaseEndpoints.bearerSystemAdminOrServicePolicyEndpoint (sets Policy.key)
                   └─ routing function from V3BaseEndpoint.systemAdminOrExportServicePolicy
                        ├─ header alg == EdDSA ─► ServiceTokenVerifier ─► ExportCaller.Service(principal)
                        └─ otherwise ─► Authenticator + ensureSystemAdmin ─► ExportCaller.Admin(user)
V3ProjectsRestService
  trigger  : createdBy from the caller; any export in the slot answers 409 export_exists with its id
  status / download / delete : lookup by id, then a Service caller must equal task.createdBy, else 404
  every Service call : one INFO audit line + bounded span attributes

    // modules/jwt — pure, JDK only
object EdDsaJwt {
  def peekHeader(token: String): Try[JwtHeader]                        // unverified; for routing and kid lookup
  def verify(token: String, key: PublicKey): Try[(JwtHeader, JwtClaim)] // alg == "EdDSA", 64-byte signature
}

// slice/security
final case class ServicePrincipal(name: ServiceName, kid: String, jti: String)
enum ExportCaller { case Admin(user: User); case Service(principal: ServicePrincipal) }

    Alternative Approaches Considered

    • HS256 with a per-server shared secret (the cheapest shape: reuse JwtCodec). Rejected: the secret mints SystemAdmin user tokens on that server, and every server would need its own client secret.
    • A real SystemAdmin service account per server. Rejected by the ticket: no account on each server, and a SystemAdmin can do everything.
    • Reuse the JWT scope claim on user tokens. Rejected: still a user, and ADR-0013 keeps Scope apart from authorization.
    • A JWT library (jwt-scala, nimbus). Rejected: the JDK verifies Ed25519 natively (JEP 339) and modules/jwt is the repo's leaf for JWT mechanics; a library adds dependencies to every image for about a hundred lines.

    Technical Considerations

    • Security. alg is pinned per key (only EdDSA reaches the verifier; HS256 or none with a service kid is rejected). The key is chosen by kid from the static map only; jku, jwk, x5u, x5c are ignored and crit is rejected. The signature is checked over the received header.payload bytes; it must decode to 64 bytes; base64url input with =, +, / or whitespace is rejected. Error messages to clients are fixed strings (dasch-specs learning shared-tapir-error-envelope-leaks-exception-messages.md): no new variant in BaseEndpoints.errorOutputs; the v3 base already prepends 401 and 403.
    • Ordering. The service check runs in the tapir security logic, before the body is decoded, like bearerSystemAdminPolicyEndpoint (learning security-logic-authenticates-body-buffering-precedes-it.md). The ownership check needs the export id from the path, so it runs in the RestService.
    • Do not reintroduce DEV-6766. Status, download and delete resolve the export by id alone (V3ProjectsRestService.scala:81-84). The ownership check compares only the task's creator and never resolves the project.
    • Persistence. FilesystemDataTaskPersistence.readTaskJson silently drops a task file that fails to decode, so a codec change that broke old files would lose the export slot's state without an error. A test decodes a literal task file in the old shape.
    • DataTaskStatusResponse is shared by exports, imports and data imports. The field stays a JSON string; a test pins the OpenAPI schema of createdBy (no snapshot test of the spec exists in the repo).
    • ADR-0013 infrastructure. Two exhaustive matches need the new case: Policy.requirement and AuthorizationMatrixE2ESpec.allowedBy (returns Some(Set(Root)), so the four export endpoints stay exempt to V3SystemAdminRoutesE2ESpec). Policy.key may only be set in slice/common/api and V3BaseEndpoint (tools/lint/check_authz.py), so the factory lives in BaseEndpoints. Domain code must not import slice/api (check_api_imports.py): TaskCreator lives in the export domain, ServiceName in slice/common/domain, ServicePrincipal and ExportCaller in slice/security. New code must not mention SystemUser.
    • Observability. The audit line follows the single-entry onExit pattern of observed in slice/api/admin/service/SparqlPassthroughRestService.scala:172-227 (it takes a User, so it is a model, not a reusable helper); attributes go on the current server span via Tracing.
    • Code conventions. Methods stay under 50 lines (split the verifier into per-claim checks); comments cite no plan or P-number; no unsafeFrom on token input; no orDie on a bad token; imports, not fully qualified names.

    Implementation Phases

    Phase 1: EdDSA verification and the trusted-key config

    • modules/jwt: add kid: Option[String] = None and a crit presence flag to JwtHeader, parsed in fromJsonString; every existing JwtHeader( call site still compiles
    • modules/jwt: add EdDsaJwt.peekHeader and EdDsaJwt.verify (alg exactly EdDSA, strict base64url checked against [A-Za-z0-9_-] before decoding, 64-byte signature, crit rejected, SignatureException mapped to a failure rather than thrown, key algorithm checked to be EdDSA/Ed25519), JDK java.security only; existing JwtCodec signatures unchanged
    • Ed25519 test signer (sign(claim, kid, privateKey)) in test sources, reachable from the jwt, webapi and e2e tests (a test-only Bazel target, or one copy per module); main code carries no signing code
    • modules/jwt tests: a token signed with a generated key verifies; a tampered payload, a signature by another key, alg HS256, none or eddsa, a 63-byte signature, a malformed signature, padded or non-url base64 and a crit header are each rejected
    • modules/jwt test: JwtCodec.decodeAll rejects an EdDSA-signed token (guards the 401 on every HS256 path, ingest included)
    • AppConfig: ServiceIdentityConfig(trustedKeys: String) under app.service-identity, trusted-keys = "[]" overridden by ${?KNORA_WEBAPI_SERVICE_IDENTITY_TRUSTED_KEYS}, added to AppConfig and AppConfigurations and projected as its own layer
    • ServiceName value type in slice/common/domain (non-empty, ^[a-z0-9-]+$, StringValue/StringValueCompanion with from returning Either, per docs/development/value-types.md)
    • Trusted-key layer: decode the JSON into a plain DTO list, then convert into an immutable Map[kid, TrustedServiceKey(name, kid, PublicKey)]; empty or whitespace-only means no keys; malformed JSON, an unparsable or non-Ed25519 key, a duplicate kid and an invalid name or blank kid each fail startup with a message naming the field and entry index, never key material; one INFO line at startup lists the count, names and kids
    • ServiceTokenVerifier (final class, ZLayer.derive) in slice/security: key by kid (missing kid = unknown_kid), verify, then iss == sub == name, normalised aud match (P2), exp/iat/jti present, 30 s leeway via ZIO Clock, exp - iat <= 15 min; returns IO[ServiceTokenRejection, ServicePrincipal] with the P9 categories as an enum; registered in SecurityModule and LayersLive

    • AppConfigSpec: the default trusts no key

    • Run just check; it passes

    Acceptance Criteria

    • With no trusted keys configured, any EdDSA token gets 401 on every endpoint (verified at verifier and factory level; the e2e server always trusts a key)
    • With a trusted key, a valid service token can trigger, poll, download and delete its own export
    • A service token gets 404 on status, download or delete of an export it did not create, whatever that export's state
    • A service triggering while any export holds the slot, its own or another caller's, gets 409 export_exists with that export's id and project (revised by the owner on 2026-11-19)
    • A service token gets 401 on every endpoint outside the four export endpoints
    • Wrong aud, unknown kid, bad signature, expired token, lifetime above 15 minutes, iss/sub not matching the key's name: each 401
    • SystemAdmin behaviour on the four export endpoints is unchanged, including access to service-created exports
    • Task files written by the previous version restore unchanged
    • DataTaskStatusResponse.createdBy stays a plain string in the OpenAPI spec (only its description changes)
    • Each service call logs one INFO line with service name, kid, jti, action, project IRI, export id and outcome; an ownership refusal is logged as not_owner
    • An export created under one key of a service stays accessible under another key of the same service
    • Malformed trusted-key config fails startup with a message that does not echo key material
    • just test-unit, just check and the e2e suite (just test-e2e) pass, including EndpointPolicyE2ESpec and AuthorizationMatrixE2ESpec

    Dependencies & Risks

    • The client (dsp-repository) does not exist yet, so the token contract is proven only against tokens our tests sign. The PR body gives the contract precisely enough to build against (H2).
    • A mis-normalised aud check would lock the client out on prod (:443). Covered by P2 and its test.
    • Changing createdBy touches imports. Covered by the old-shape decode test and the unchanged string wire format.
