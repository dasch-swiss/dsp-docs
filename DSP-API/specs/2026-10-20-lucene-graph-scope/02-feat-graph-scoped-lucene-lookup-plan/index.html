    feat: Project-scope the Lucene lookup in Gravsearch and /v2/search

    Overview

    The Fuseki text index stores each indexed triple's named graph since dsp-api#4393 (text:graphField "graph"), and every host rebuilds its index on the first start of an image that carries it (DEV-7589, dsp-api#4394). dsp-api does not use the field yet. This plan wraps the Lucene statement of every project-restricted fulltext lookup in GRAPH <projectDataGraph> { ... }: Gravsearch matchFulltext, matchText, matchTextInStandoff, matchLabel, and /v2/search (page, count and breadth probe). The design is ADR-0012; its Decisions 1–7 are binding, except that Phase 6 amends Decision 6 (see Open questions) and narrows Decision 2's wording to the main-resource rule. The evidence is the measurements and the dev re-run on DEV-7377.

    Problem Statement / Motivation

    A project-restricted fulltext search runs an unscoped ?s text:query ..., pays the per-hit joins for the whole repository's hits, and only then drops the out-of-project ones with attachedToProject. Measured on dev with real scoping (count queries, warm medians): Gravsearch matchFulltext at the 10k cap goes from 0.66–3.18 s to 0.19–1.53 s; with the 1M limit from up to 18.7 s to at most 4.7 s; /v2/search with the 1M limit from up to 30 s to at most 4.6 s (class-restricted L4: 13.8 s, the class walk). Because the cap applies after scoping, 6 of the 11 prod cases truncated today come back complete. This is also what makes DEV-7492 (lifting the cap) affordable for restricted searches.

    Proposed Solution

    1. Model. Add GraphPattern(graph, statement) to the prequery model, rendered GRAPH <g> { ... }, opaque to every pass like GroupPattern and SubSelectPattern. It wraps exactly one statement, the text:query one.
    2. Resolve once, through a port. Search declares a port ProjectDataGraphs in slice/search/ports (ADR-0011 Decisions 2, 6 and 9: a new cross-context read goes through a consumer-defined port). Its adapter ProjectDataGraphsLive in slice/admin/domain/service resolves a ProjectIri with KnoraProjectService.findById and ProjectService.projectDataNamedGraphV2, the one derivation of the graph IRI. SearchResponderV2Live resolves limitToProject through it once per request into an Option[FulltextProjectRestriction] (Scoped or Unresolved), which both search paths use. An unknown project is Unresolved: the query stays exactly as today (unscoped lookup + attachedToProject, which returns nothing).
    3. Gravsearch. Pass the graph of a Scoped restriction into GravsearchToPrequeryTransformer / GravsearchToCountPrequeryTransformer → AbstractPrequeryGenerator, and wrap only the text:query statement in a GraphPattern, and only when the lookup is anchored on the main resource (see "Which lookups may be scoped" below). attachedToProject on the main resource stays.
    4. /v2/search. SearchFulltextQuery.build and buildProbe wrap only the text:query statement inside the inner SELECT DISTINCT ?matchingSubject when the restriction is Scoped, and build then drops the attachedToProject line. The class restriction (subClassOf* walk) is unchanged.
    5. Tests, docs, dev verification as listed in the phases.

    What is inside and outside the GRAPH block, per lookup:

    Lookup Inside GRAPH <g> { } Stays on the union graph
    matchFulltext the text:query statement, inside the existing SELECT DISTINCT subselect value branch, list-node branch, BIND(COALESCE(...)), creationDate probe, type FILTER NOT EXISTS
    matchText (both schemas) ?textVal text:query ("term" limit) everything else the query has
    matchTextInStandoff the text:query statement valueHasString, standoff start/end, the REGEX filters
    matchLabel ?res text:query ("term" limit) everything else
    /v2/search page and count ?matchingSubject text:query (term limit) standoff filter (inside the subselect, outside GRAPH), both OPTIONALs, resource probe, class walk
    /v2/search probe the same statement the standoff filter

    Why only the Lucene statement (PRD REQ-6.3 trap, ADR Decision 2): rdf:type checks against knora-base classes, rdfs:subClassOf* and inferred-property VALUES resolve against ontology graphs, and a blanket GRAPH <dataGraph> around them returns zero rows. The data-only patterns (value branch, list branch) gain nothing from GRAPH either (engine Fact 5: bound-subject lookups across the union are free), so they stay outside and the change stays one statement wide.

    The list-node branch (ADR Decision 3) needs no extra code: its anchor ?match comes from the scoped lookup, so the matched list node is already in the project data graph. What makes that complete is a data fact, not the query: no list value points into another project's graph or into the system lists (0 of 1.69 M valueHasListNode triples on stage, 2026-10-20; the platform does not allow it). Phase 1 re-checks it together with the resource invariant. No UNION with the system-lists graph.

    Prior decision revisited. The DEV-6864 plan (dasch-specs 2026-07-24-sparql-performance-remediation, R16) made the breadth probe ignore the project, because "a project restriction does not reduce cost", and said to revisit when DEV-6809 (c) makes restricted queries cheap. Scoping the lookup is that change: the scoped probe is 1.0–4.3× cheaper and counts only in-project hits (DEV-7377), so the probe now mirrors the restriction (ADR Decision 4).

    Technical Considerations

    Which lookups may be scoped. limitToProject restricts the main resource (it becomes ?mainRes knora-base:attachedToProject <p>). A Lucene lookup anchored elsewhere, for example matchFulltext(?other) on a linked resource (the E2E spec already tests this shape) or matchText on a value of a linked resource, may legitimately hit another project's graph, since links across projects are allowed. Scoping those would silently drop results. Rule:

    • matchFulltext(?r, ...) and matchLabel(?r, ...): scope iff ?r == mainResourceVariable.
    • matchText(?v, ...) / matchTextInStandoff(?v, ...): scope iff ?v is the object of at least one input statement, every input statement with object ?v has the main resource as subject, and none of them has the predicate rdfs:label (a label variable is a literal, not a value).
    • Otherwise: emit unscoped, as today.

    The anchored set is computed in one pre-pass over the whole input WHERE (after type annotations are removed), before generation. It must not be recorded while processing statements, and it must not read the generator's literalVariables: both would be filled in traversal order, which puts a filter before a later OPTIONAL/UNION's statements, so a per-statement record would scope ?v in a UNION where another branch binds it from a linked resource, or miss a label statement that follows the filter. The pre-pass is a pure function of the input patterns and the main resource variable, a local fold that recurses into OPTIONAL, UNION, MINUS and FILTER NOT EXISTS the way QueryTraverser.visitWherePatterns does (that is an instance method with three injected callers, and the generator has no QueryTraverser, so it is not reused). The generator does not see the WHERE at construction (it is built from the CONSTRUCT clause, SearchResponderV2.scala:780 and :864), so the input patterns travel with the scope: LuceneScope(dataGraph: InternalIri, inputWhere: Seq[QueryPattern]), and the generator computes the anchored set lazily from it and its own mainResourceVariable.

    The ticket asks for the same treatment of all four functions unconditionally; ADR Decision 2 says "where a project restriction is known". This plan follows the ADR (see Open questions).

    Pattern passes. QueryPattern is sealed, but only some matches are exhaustive. -Werror lists QueryTraverser.transformWherePatterns (opaque pass-through), GravsearchTypeInspectionUtil.transformPattern (opaque), PrequeryPatternOrdering.partition (a unit) and vars (the inner statement's variables: unlike a subselect, a GRAPH block exposes its bindings), and the test helper GravsearchInferencePipelineTestSupport.shapeSummary (test-it). containsLucene, tierNum, hasProjectDataPredicate and unitKey in PrequeryPatternOrdering end in case _ defaults, would silently rank the new pattern T7, and must be edited by hand. Because GraphPattern holds one StatementPattern, they delegate to it: the tier is the inner statement's tier, and the key is unitKey(g.statement, ...).copy(unit = g). That copies the restricted terms, loop variables and the final sparql tie-break (PrequeryPatternOrdering.scala:361, rank at :383), which would otherwise compare GRAPH <...> { against ?s <... text, so a query with one scoped and one unscoped Lucene unit keeps its order. containsLucene must reach the GraphPattern: the matchFulltext group is T1 only because the check reaches the text:query inside its subselect, and that statement now sits one level deeper. Missing this silently demotes the group and changes the join order. Non-exhaustive sites with a default (ConstructTransformer, InferenceOptimizationService, GravsearchQueryOptimisation.StatementsFirst, SelectTransformer, SearchResponderV2.flattenPatterns, visitWherePatterns) need no change; the main query never sees the pattern, and the input WHERE never contains one.

    Wrapping turns the Lucene statement of matchText, matchLabel and matchTextInStandoff from a triple inside a BGP into a GRAPH block, which Jena evaluates as a separate element (engine Fact 1). T1-first ordering is what makes that neutral: the Lucene unit runs first and the rest is substituted per row. This is why the Phase 1 ordering tests are load-bearing and why Phase 7 times these functions.

    The bare Lucene statement emitted by transformFilter is traversed again in transformSelectToSelect (stage two) and goes through SelectTransformer → OntologyInferencer.inferSubproperties. A wrapped one is opaque and skips that pass. That is a no-op for text:query (it has no subproperties); unscoped queries keep the current path. The scoped goldens, which run the full inference pipeline, pin it.

    Rendering. GraphPattern(graph: InternalIri, statement: StatementPattern), toSparql = GRAPH <${graph.value}> {\n...}\n (InternalIri has no render method). The graph IRI is derived from validated Shortcode/Shortname value objects, so there is no injection surface. In SearchFulltextQuery, use the sparql"..." interpolator with an Iri hole (GRAPH ${Iri.unsafeFrom(graph.value)} { ... }, as the file already does for the project IRI).

    /v2/search signature. Replace limitToProject: Option[ProjectIri] in build with an explicit restriction type, so "scoped" and "unknown project" cannot be confused:

    enum FulltextProjectRestriction {
  def project: ProjectIri
  case Scoped(project: ProjectIri, dataGraph: InternalIri) // GRAPH-wrap the lookup, no attachedToProject
  case Unresolved(project: ProjectIri) // unknown project: today's attachedToProject line, which matches nothing
}

    build, buildProbe and FulltextBreadthGuard.guarded all take the same Option[FulltextProjectRestriction]; the probe mirrors only Scoped (an Unresolved probe stays unscoped, as today). BreadthKey.project stays restriction.map(_.project.value), and the probe SPARQL in the key differs per graph, so a scoped and an unscoped probe never share an entry. guarded has two callers, both in SearchResponderV2. Behaviour change, intended: the cap now applies to the in-project candidate count, so a term refused today for a small project passes once scoped; the guard's Scaladoc says so. The refusal message stays as it is ("matches too many candidates" is still accurate).

    Graph resolution. One function in the SearchResponderV2Live companion, resolveRestriction(port: ProjectDataGraphs, limitToProject: Option[ProjectIri]), turns the parameter into Task[Option[FulltextProjectRestriction]] (ZIO.foreach over the option, fold on the port's answer), so it can be unit-tested with an in-memory port. It runs only when limitToProject is set: for Gravsearch inside the gravsearch.prequery.generate stage span, before the transformer is constructed (the scope is a constructor parameter); for /v2/search before SearchFulltextQuery.build and guarded (the guard forks the query), outside the translateSearchTimeout scope. A failing lookup (triplestore error) fails the request; it never silently falls back to unscoped. Only "project not found" yields Unresolved. A built-in project IRI (ProjectIri accepts them, KnoraProjectRepoLive.findById returns them) resolves to its derived graph like any other project. The lookup also runs for Gravsearch calls with limitToProject but no Lucene function (the internal incoming-link and representation searches); that is accepted: known projects hit the cache, and a triplestore failure there would fail the query anyway.

    Dropping attachedToProject in /v2/search. The ticket asks for it (what remained of DEV-6809 (c)). It is correct iff every resource reached from an in-graph hit is attached to that project: a value's owning resource, a label's own resource and a list value's resource all live in the same data graph as the hit. Keeping the join would protect against one failure mode: the value and list branches resolve the resource through unconstrained joins, so a value or list value in project Q's graph that points at a hit in P's graph would return a Q resource for a search scoped to P. Phase 1 therefore checks on stage (a nightly prod mirror, so this covers prod data) that resources, their values and the list values' list nodes all share one graph per project, and Phase 7 compares counts with and without the join on dev. If the stage check finds a violation, the plan keeps the join (see Phase 1). Gravsearch keeps its attachedToProject: it restricts the main resource, which need not be the Lucene anchor.

    Performance. Scoping removes out-of-project hits before any join (numbers above). The /v2/search class walk remains the cost for class-restricted searches (non-goal, separate ticket). Known projects add no round trip after the first request per node (the KnoraProjectRepoLive entity cache); CachingEntityRepo caches hits only, so an unknown project IRI costs one admin-graph query per request.

    In-memory triplestore double. TriplestoreServiceInMemory has no text index (FulltextBreadthGuard's Scaladoc relies on this: the probe fails there by construction), so any text:query returns nothing there, scoped or not. Nothing that executes a scoped lookup can be tested against it. Execution tests run in test-it and test-e2e against the Fuseki testcontainer (FUSEKI_IMAGE = daschswiss/apache-jena-fuseki:latest, whose dsp-repo.ttl carries graphField). A stale local :latest from before #4393 has no graph field, so a GRAPH clause around text:query is a no-op there (modules/fuseki/dsp-repo.ttl, Fact 10), and almost every scoped test still passes: Gravsearch keeps attachedToProject, so its "other project → 0" cases hold either way. Only tests that bypass that join detect the stale image: the /v2/search count scoped to another project (the join is dropped there) and a direct GRAPH <other project's graph> { ?s text:query ... } query in test-it (Phase 2). The Phase 2 image check is the primary guard.

    Test data. test_data/project_data/books-data.ttl is loaded into http://www.knora.org/data/0001/books, a second graph for project 0001, so a scoped search for 0001 does not see those resources (the known exception to "one project, one graph", test data only). No current spec combines limitToProject with books data (checked SearchResponderV2Spec, MatchFulltextE2ESpec); running the search suites in Phase 5 catches one if it exists. The MatchFulltextE2ESpec fixture is loaded only by that spec, so moving it into the 0001 data graph does not touch other specs' data.

    Golden mechanics (docs/development/dsp-api-conventions.md, "Golden snapshot tests"). A new golden needs an empty placeholder file under src/test/resources/... before the rewrite run. test-it goldens are rewritten with --test_env=GOLDEN_REWRITE=1; webapi's GoldenTest ignores that variable, so there rewrite = true on the call is the only route, removed again before commit. SearchFulltextQuerySpec is not a GoldenTest today (it compares canonicalised legacy fixtures); its new cases mix in webapi's org.knora.webapi.GoldenTest and are exact-text goldens, while the legacy cases stay canonicalised. A clean re-run follows every rewrite. --test_filter is a Java regex: '.*Spec.*', never a leading bare *. The test harness passes limitResultsToProject and the scope separately; the scoped goldens derive the graph from the same project, so they never pair a graph with no attachedToProject or the reverse.

    Dependencies & Risks

    • An index without the graph field. A host that runs a scoped query against an index built before the field was configured returns zero scoped hits (modules/fuseki/dsp-repo.ttl, modules/fuseki/README.md); a host whose config lacks the field ignores the GRAPH clause. Mitigation: H3. The field and the rebuild arrive together through DEV-7589. Dev is rebuilt (2026-10-21); stage and prod rebuild on their first deploy of the new Fuseki image.
    • One project, one graph. Scoping misses any resource of project P outside P's derived data graph (the test data has one: data/0001/books), and dropping the join would let a value or list value in another graph pull in a foreign resource. Phase 1 checks stage; on a violation the plan keeps the join in /v2/search and goes on. Phase 6 records the rule in the Resources & Values CONTEXT.md.
    • Cross-project anchors. Handled by the main-resource rule; goldens pin the unscoped form for linked anchors and a Phase 5 E2E runs it against a resource in another project's graph.
    • Silent T1 demotion. If containsLucene does not reach GraphPattern, the matchFulltext group loses T1 and the join order changes. Phase 1 adds an ordering test; the new ...Shape goldens show it too.
    • Golden churn. None: the existing SearchFulltextQuerySpec legacy fixtures stay byte-unchanged (their tests switch to Unresolved), and Gravsearch only gains new goldens, because no existing one combines a project limit with a Lucene lookup.
    • Local test image. A stale local daschswiss/apache-jena-fuseki:latest ignores the GRAPH clause, and most scoped tests still pass (Gravsearch keeps attachedToProject); Phase 2 loads and checks the image, and the test-it detector and the /v2/search 0803 count fail on a stale one. CI uses the image published from main, which has the field.
    • The probe fails open. A malformed scoped probe would be swallowed by the guard; the probe golden covers its syntax, and the E2E two-term search runs it against Fuseki.
