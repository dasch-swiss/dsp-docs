    Build Baselines

    The numbers the build-system migration (DEV-7767) is compared against. A later run that differs from them is a defect to explain, not a new baseline.

    How the numbers are produced

    Number Command
    Passing spec files, passing and skipped tests per library scripts/test-counts.sh
    The same, for the Bazel test targets, after just test scripts/test-counts-bazel.sh
    Bundle inventory just build, then scripts/bundle-inventory.sh bazel-bin/apps/dsp-app/dist (before the migration: pnpm exec nx build dsp-app over dist/apps/dsp-app)
    Hash of a generated tree scripts/tree-hash.sh <dir>
    Stories just storybook-build, then the type: story entries of bazel-bin/storybook/index.json (before: pnpm run build-storybook over dist/storybook)
    Storybook interaction tests just storybook-test (before: pnpm run test-storybook against that build)
    Cypress specs find apps/dsp-app/cypress -name '*.cy.ts'

    scripts/bundle-inventory.sh replaces the content hash in a file name with [hash], so two builds of different sources list the same names.

    When two runs match

    • Test counts: every line equal.
    • Two Angular CLI bundles: the normalized file list is equal and the total size is within 10 percent.
    • The Angular CLI bundle against a Bazel bundle: the initial files (main, polyfills, styles) are each within 10 percent, and the number of lazy chunks is equal. Chunk names and splitting differ between the two bundlers, so nothing else is compared.

    Pixeleye under the playwright-core 1.59.0 hold

    The @pixeleye/cli-install>playwright-core override resolves 1.59.0 for that package alone, and importing it raises no ERR_PACKAGE_PATH_NOT_EXPORTED. Pixeleye uses two Playwright versions:

    • pixeleye runs @pixeleye/cli-install's installBrowsers() each time it starts its snapshot server, which downloads Chromium, Firefox and WebKit for 1.59.0 (chromium v1217) and runs installDeps. It needs a writable browser directory.
    • @pixeleye/cli-capture launches the browser through the root playwright-core, 1.61.1 (chromium v1228), the playwright-driver version of the locked nixpkgs.

    CI run 42118134666 (Node 24.22.1) captured 811 stories and 24 breakpoint stories with that split, the CLI downloading its own 1.59.0 browsers. Phase 9 therefore gives the Pixeleye job a writable PLAYWRIGHT_BROWSERS_PATH, not the read-only Nix store path: the CLI's own 1.59.0 download, plus chromium-headless-shell for 1.61.1 from playwright-core install. The Nix browsers cannot be linked in: on start the CLI deletes every browser in the directory that no installed Playwright registered (CI run 42261938720).

    Generated paths: direct-only

    A library's generated tsconfig maps only the aliases of its declared deps to their compiled .d.ts. An import of a library that is not a declared dependency fails with TS2307, so no separate undeclared-import check exists.

    The choice rests on one comparison, run on a throwaway build of the spike's last commit (0587a5737), with every library's paths generated once as the transitive closure and once as the direct deps only. The three resource-editor components the spike reported as changed (geolocation-value, authorship-form-field, create-resource-form-legal) were compared by the dependencies array of their ɵɵdefineComponent, the template's directive imports:

    Compile Result for the 3 components
    Closure against direct-only, persistent worker byte-identical .js
    Closure against direct-only, clean output base, no worker byte-identical .js
    Bazel against the Angular CLI's program (ngc -p apps/dsp-app/tsconfig.app.json, same sources and compiler) same directives in the same order; MatFormField, MatLabel, MatHint and MatError come from @angular/material/form-field in Bazel and from @angular/material/input in the CLI's

    The CLI difference is the module specifier of the same class: @angular/material/input re-exports those four directives from the form-field chunk, and each component imports both MatFormFieldModule and MatInputModule, so either specifier names the one class. The spike's reported difference is the same kind: MatOption, re-exported by both @angular/material/select and @angular/material/autocomplete, named through one or the other. Which specifier the compiler writes depends on which declaration files the program loaded, not on the shape of paths, and it does not change what runs. The spike's difference did not reproduce under either build of the same commit; the build it came from was not kept.

    Jest does not read the generated paths: jest.resolver.js falls back to TypeScript's resolution against tsconfig.base.json, which lists every alias. A library's test therefore holds to its declared deps only through its runfiles, which carry the sources of those deps and nothing else. Seeded check on core/session, whose error-handler dependency no other dep of it carries: with //libs/vre/core/error-handler removed from deps, bazel test //libs/vre/core/session:test fails three of five suites with Cannot find module '@dasch-swiss/vre/core/error-handler' in the local darwin sandbox. The resolver follows the runfiles symlinks into the execroot's output tree, where a missing dependency's sources are absent as long as nothing copies them there; remote execution, whose inputs are the declared ones only, holds without that condition.
